# Colab T4 上にローカル LLM を立て、ノートブックのターミナルから Cline で AI コーディングする

- 版: v2.4（v1.0 のブラウザ IDE 構成を全面的に置き換え）
- 作成日: 2026-09-03
- **v2.4 での訂正（実機デバッグで判明）:** T4 上で実際にセットアップして実タスクを
  流したところ、次の 3 点が判明し、スクリプトを修正した。
  1. **既定モデル `qwen2.5-coder:7b-instruct-q4_K_M` は Cline から一切ファイルを
     書けない。** `ollama show` は `Capabilities: tools` を名乗るが、実際には
     Ollama が要求する `<tool_call>...</tool_call>` ラッパーに従わず、生の JSON を
     素のテキストとして返す（temperature=0 でも 100% 再現）。Cline はそれを
     ツール呼び出しと解釈できないため、チャットで「作りました」と説明するだけで
     ファイルは 1 つも作られない。既定モデルを `qwen3:8b` に変更した。§5.6
  2. **Cline CLI 3.x では `cline config set key=value` が廃止されている。**
     `error: too many arguments` で失敗する。非対話設定は
     `cline auth -p <provider> -m <model> [-b <baseurl>] -k <apikey>` に変わった。
     `cline config`（引数なし）も対話専用になり、TTY が無いここでは使えない。§6.2
  3. **Cline CLI 3.x はコマンドライン引数に日本語（非 ASCII 文字）が混ざると
     `Unknown command or unquoted prompt` で必ず失敗する。** 標準入力経由なら
     同じ文字列でも問題なく処理される。`50_run.sh` を標準入力経由に修正した。§7.2

  あわせて `common.sh` の ERR トラップが `set +e` を敷いていても発火してしまう
  bash の罠を修正した（`30_cline_cli.sh` が最初の設定コマンドで即 FATAL していた
  実際の原因）。
- **v2.1 での訂正:** v2.0 で「無料枠にターミナルは無い（Pro 限定）」と書いたのは**誤りでした。**
  2020 年の Pro 向け発表を根拠にしており、5 年古い情報でした。
  **2025 年 6 月 23 日に Google が全ユーザーへ無料開放しています。**（§3.3 に根拠）
  これに伴い §3・§4 を書き直し、`colab-xterm` による回避は不要になりました。
- **v2.2 での追加:** 30 秒タイムアウトは Cline CLI 固有の制約であり、`--timeout` を
  設定できる代替エージェント（aider / Qwen Code など）がある、という調査結果を §7.1 に追加。
  導入スクリプト `scripts/31_alt_agents.sh` も追加しました。
- **v2.3 での追加:** Codex CLI（Cline に最も近い自律エージェント）を §7.1 と
  `31_alt_agents.sh` に追加。Colab でのサンドボックス・コンテキスト長・tool calling の注意も記載。
  スクリプトを VM に置く方法（VS Code 拡張の `Upload to Colab` ほか）を §3.4 に追加しました。
- 前提: Google Colab **無料枠** / T4 GPU / Cline は Colab VM 上で動かす
- 関連:
  - `claude/colab-t4-local-llm-design.md` — Colab CLI でジョブを流す構成（別用途）
  - `archive/browser-ide/` — v1.0（code-server / トンネル構成）。**もう使いません。**§2 に理由

## 0. 先に結論

| 論点 | 結論 |
|---|---|
| 何を作るか | Colab VM 上に Ollama と **Cline CLI** を置き、ノートブック UI の中から使う |
| 外部トンネル | **不要になった。** ngrok も cloudflared も dev tunnels も使わない |
| v1.0 からの変化 | 規約リスクが「高〜最高」から「低〜中」へ大きく下がった。§2 |
| 無料枠でターミナルは使えるか | **使えます。** 2025-06-23 に全ユーザーへ無料開放済み。ノートブック下部のツールバーの「ターミナル」 |
| 使い方 | ターミナルで `cline` を対話実行するのが本命。セルからのヘッドレス実行も併用できる。§4 |
| 最大の技術的リスク | **Cline CLI の Ollama リクエストが 30 秒でタイムアウトする**（[cline#9182](https://github.com/cline/cline/issues/9182), [#9484](https://github.com/cline/cline/issues/9484)）。CLI 側に設定項目が無い。§7 |
| それは避けられるか | **Cline 固有の制約です。** Codex CLI・Qwen Code・aider はいずれもタイムアウトを設定できる。§7.1 |
| モデル | **8B 級（qwen3:8b）を既定にした。** 30 秒の壁の下では「賢さ」より「prompt eval の速さ」が実用性を決める。ただし qwen2.5-coder:7b は Ollama の tool-calling に従わず実質使い物にならないため除外した。§5 / §5.6 |
| 最大の運用リスク | 12 時間でセッションごと消える。書いたコードは git push する以外に守る手が無い |

## 1. 構成

```
ブラウザ（Colab ノートブック UI）
  │
  ├─ ターミナルウィンドウ（本命）
  │     下部ツールバーの「ターミナル」ボタン
  │     → 全ユーザーが無料で使える（2025-06-23〜）
  │     $ cline
  │
  └─ セルから直接（自動化・非対話向け）
        !bash scripts/50_run.sh "やってほしいこと"
              │
              ▼
      ┌───────────────────────────────────────────┐
      │ Colab VM (T4 16GB) ※12時間で消える          │
      │                                           │
      │  Cline CLI  ──HTTP──> Ollama 127.0.0.1:11434│
      │     │                    └ 7B Q4_K_M       │
      │     │                       num_ctx=32768  │
      │     ▼                                      │
      │  /content/workspace                        │
      │     └ .cline/rules/local-model.md          │
      └───────────────────────────────────────────┘
```

**要件はこれで全部満たせます。**

1. Cline が Colab VM 側で動く → `127.0.0.1:11434` がそのまま Ollama
2. Cline のターミナル実行が VM 上で走る → T4 がそのまま使える
3. ブラウザから触れる → Colab のノートブック UI がそれ

## 2. v1.0（ブラウザ IDE 構成）から何が変わったか

v1.0 では「ブラウザで VS Code の UI を動かす」と読んで設計していました。
そのため VS Code の UI をブラウザに届ける経路が必要になり、以下を検討していました。

| v1.0 の経路 | 手段 | 規約リスク |
|---|---|---|
| A | Colab 内蔵ポートプロキシ + code-server | 中 |
| B | VS Code Remote Tunnel → vscode.dev | 高 |
| C | Cloudflare Quick Tunnel + code-server | 最高 |
| D | Google 公式 Colab VS Code 拡張 | 低（ただし Ollama に届かず不成立） |

**「ターミナルウィンドウ」だったのなら、この 4 経路は全部不要です。**

- Cline には CLI 版があり（`npm i -g cline`）、VS Code 拡張と同じエージェントが端末で動く
- ターミナルは Colab のノートブック UI が**全ユーザー向けに**すでに持っている（§3.3）
- したがって **code-server も、外部トンネルも、公開 URL も、WebSocket の心配も消える**

### v1.0 の経路 D の評価も変わりました

v1.0 では「Google 公式 Colab VS Code 拡張は Ollama に届かないので不成立」と書きました。
これは **Cline を VS Code 拡張として動かす前提での話**です。Cline 拡張は手元の PC の
拡張ホストで動くため、`127.0.0.1:11434` が手元の PC を指してしまう、という理屈でした。

**Cline CLI を使うなら話が別です。** この拡張には実験的機能として
「Colab Terminal」（`Colab: Open Terminal`）があり、**Colab ランタイムに繋がった
ターミナル**が開きます。そこで `cline` を起動すれば、Cline は VM 上で動くので
`127.0.0.1:11434` はちゃんと VM の Ollama です。

つまり **経路 D は Cline CLI と組み合わせれば成立します**（§4 の T3）。
`archive/browser-ide/43_colab_vscode_note.md` の結論は、CLI を考慮していない点で
今は不正確です。VM 側にターミナルが取れるという事実のほうが重要でした。

## 3. 規約の評価

Colab のよくある質問に記載された禁止事項に照らします。

### 常時禁止（無料・有料問わず）

| 項目 | 本構成の該当性 |
|---|---|
| リモートプロキシへの接続 | **該当しない。** 外部トンネルを 1 本も張らない |
| ファイルホスティング、メディア配信、Colab との相互作用的コンピューティングに関係のないウェブサービス | **該当しない。** 公開 URL を持たない。Ollama は 127.0.0.1 のみ |
| 大量データのダウンロード、P2P | 該当しない |

**v1.0 で最大の懸念だった「リモートプロキシ」が構成から消えました。** これが最大の改善です。

### 無料枠でのみ追加禁止

| 項目 | 本構成の該当性 |
|---|---|
| SSH シェル、リモートデスクトップなどのリモートコントロール | **該当しないと解する。** §3.3 |
| ノートブック UI をバイパスした、主にウェブ UI を介したやり取り | **該当しない。** ノートブック UI の中で完結する |
| 分散コンピューティングワーカーの実行 | 該当しない |

### 3.3 ターミナルは無料枠で使える（v2.0 の記述を訂正）

**v2.0 では「Colab 標準のターミナルは Pro 以上の機能」と書きましたが、誤りでした。**
根拠にしていたのは 2020 年 12 月の "Colab Pro: now with a Terminal!" という発表で、
5 年古い情報でした。

その後 **2025 年 6 月 23 日、Google はターミナルを全ユーザーに無料開放しています。**

> "we're taking another step in that direction by bringing terminal access to
> ALL Colab users, free of charge."
> — Spencer Shumway（Google, Colab プロダクトマネージャ）、
> [Colab Terminal Is Now Free For All Users](https://medium.com/google-colab/colab-terminal-is-now-free-for-all-users-9a10eaef2ca8)（Colab 公式 Medium、2025-06-23）

日本語圏でも同日付で報じられています（[gihyo.jp](https://gihyo.jp/article/2025/06/ai-first-google-colab)）。
また、Colab の VS Code 拡張にも「Colab Terminal」があり、こちらも
Colab ランタイムに繋がったターミナルが開きます（プラン条件の記載なし・実機で確認済み）。

**この事実は規約解釈にも効きます。**
FAQ の無料枠向け禁止事項には今も「SSH シェル、リモートデスクトップなどのリモートコントロール」
が残っています。しかし Google 自身が無料ユーザーにターミナルを提供している以上、
この条項が禁じているのは **VM に外部からの遠隔アクセス手段を立てること**
（sshd を上げる、VNC を晒す、外部トンネルで常時繋ぐ）であって、
**Colab が公式に提供する UI からシェルを使うこと**ではない、と読むのが自然です。

結果として、`colab-xterm`（`%xterm`）による回避は **もう必要ありません。**
v2.0 で「Pro 限定機能の迂回にあたる」と注意書きしていた論点は、前提ごと消えました。

> 規約文言の解釈部分は Google の公式見解ではありません。最終判断は自己責任で。
> ただし「ターミナルが無料で使えるかどうか」は解釈ではなく事実で、上記が根拠です。

## 3.4 スクリプトを Colab VM に置く方法

`/content` にファイルを送る手段は経路によって違います。

### VS Code の Colab 拡張を使っている場合（一番簡単）

**VS Code の Explorer view でファイル/フォルダを右クリック → `Upload to Colab`。**
複数選択もできます。送り先のサーバを選ぶダイアログが出るので、
接続中の Colab ランタイムを選んでください。転送後は Contents view で確認できます。

zip を送った場合は、ターミナル（`Colab: Open Terminal`）で展開します。

```bash
cd /content && unzip -oq colab-cline.zip && ls colab-cline
```

### ノートブック UI を使っている場合

- **左サイドバーのファイルペインにドラッグ&ドロップ** — 一番手軽
- またはセルから:

```python
from google.colab import files
files.upload()          # ファイル選択ダイアログが出る
```

```python
!unzip -oq colab-cline.zip -d /content/
```

> `files.upload()` は Colab のフロントエンド JS に依存します。
> **VS Code の拡張経由では動きません。** その場合は上の `Upload to Colab` を使ってください。

### git を使う場合（セッションをまたぐなら結局これが必要）

**セッションは 12 時間で消えます。**アップロードは毎回やり直しになるので、
継続して使うなら自分の GitHub に置いてしまうのが結局は速いです。

```bash
cd /content && git clone https://github.com/ip-sandbox/colab-ollama.git colab-cline
```

リポジトリ名は **`colab-ollama`**。配置先の
`/content/colab-cline` とは名前が違うので、clone 先を明示しています。

> **public なのにパスワードを聞かれる場合**、ほぼ確実に URL の綴り違いです。
> GitHub は「存在しない」と「権限がない」を区別せず両方 404 を返すため、
> git は private かもしれないと解釈して認証を求めます。
> `GIT_TERMINAL_PROMPT=0 git ls-remote <URL>` で切り分けられます。

書いたコードを守る手段としても、どのみち git は要ります（§8）。

### Google Drive を使う場合

zip を Drive に置いておけば、セッションごとにアップロードし直さずに済みます。

- VS Code 拡張: コマンドパレット → `Colab: Mount Google Drive to Server...`
- ノートブック: `from google.colab import drive; drive.mount('/content/drive')`

```bash
cp /content/drive/MyDrive/colab-cline.zip /content/ && cd /content && unzip -oq colab-cline.zip
```

`OLLAMA_MODELS` を Drive に向けてモデル自体を永続化する案もありますが、
無料 Drive は 15GB 上限で I/O も遅く、逆効果になることがあります（§8）。

### 3.5 GPU が取れないときの再試行はどこまで許されるか

T4 は無料枠では取り合いになっており、`Service Unavailable`（503）が普通に返る。
`remote/01_new.sh` は `COLAB_NEW_RETRIES` で再試行できるが、**どの程度なら
妥当か**を整理しておく。

**FAQ が明示的に禁じているのは「回避」であって「再試行」ではない:**

| FAQ の禁止事項 | 再試行の該当性 |
|---|---|
| 複数アカウントでアクセス/リソース制限を回避する | 該当しない。単一アカウント |
| コンテナ化等で不正利用防止ポリシーを回避する | 該当しない |
| ファイルホスティング / P2P / マイニング / パスワードクラック | 該当しない |

単一アカウントで「空いていますか」と問い合わせて 503 を受け取ることは、
制限の *回避* ではなく制限に *従っている* 状態である。

**ただし「列挙されていない = 安全」ではない。**

> "Colab does not publish these limits, in part because they can vary over time."
> "...may be terminated at any time without warning"
> — Colab FAQ

**明文化されていない不正利用検知が存在し、措置は警告なく行われる**と Google 自身が
書いている。短い間隔で何時間も assign エンドポイントを叩くのは人間の使い方から
乖離しており、アカウント停止までは行かずとも、レート制限や一時的な利用制限を
招く筋の行為である。

#### 実装した歯止め

| 対策 | 内容 |
|---|---|
| 既定間隔 | **300 秒**（当初 60 秒にしていたが引き上げた） |
| 下限 | 60 秒未満を指定すると警告して 60 秒に引き上げる |
| ジッター | ±20% のばらつきを入れ、同期した一斉ポーリングを避ける |
| 長時間の警告 | 総ポーリング時間が 60 分以上になる設定では警告する |
| 既定の再試行回数 | **0**（明示しない限り 1 回で諦める） |

**推奨は `--retry 3`〜`5` 程度。** それで取れなければ時間帯を変えて出直すほうが、
張り込み続けるより安全で、かつ実際に早い（空きは時間帯に強く依存する）。

> 規約文言の解釈部分は Google の公式見解ではない。最終判断は自己責任で。

## 4. 使い方の 3 形態

| | 形態 | 無料枠 | 規約 | 向いている場面 |
|---|---|---|---|---|
| **T1** | Colab ノートブック UI のターミナル + `cline` 対話 TUI | ○ | ◎ | **既定。** 試行錯誤しながら進める |
| **T2** | ノートブックのセルから `!bash scripts/50_run.sh "..."` | ○ | ◎ | 自動化・非対話・タスクを投げて結果だけ見る |
| **T3** | Colab VS Code 拡張の「Colab Terminal」 + `cline` | ○ | ◎ | 手元の VS Code を使いたい場合 |

3 つとも Google 公式の機能の上に乗っているので、規約上の差はありません。好みで選べます。

### T1: ノートブックのターミナル（推奨）

ノートブック下部のツールバーにある **「ターミナル」ボタン**を押すだけです。
VM に繋がったシェルが開きます。

```bash
cd /content/workspace
cline                 # 対話セッション
cline -p "..."        # Plan モードで開始
cline --yolo "..."    # 承認をスキップ
cline doctor          # 設定の診断
```

**注意: ターミナルはノートブックのカーネルとは別のシェルです。**
セルで `os.environ[...]` に入れた値は引き継がれません。
`scripts/40_terminal_setup.sh` が `~/.bashrc` に必要な環境変数と `cd` を仕込むので、
セットアップ時に一度実行しておいてください。

### T2: セルから（自動化向け）

```python
!bash scripts/50_run.sh "fizzbuzz.py を作って 1〜30 を出力して実行して"
!bash scripts/50_run.sh -p "このリポジトリの構成を調べて改善案を3つ挙げて"   # Plan モード
!bash scripts/50_run.sh --json "TODO コメントを列挙して"                     # NDJSON 出力
!AUTO_APPROVE=0 bash scripts/50_run.sh "README を書き直して"                 # 対話承認
```

`50_run.sh` は実行前に「Ollama は生きているか」「モデルは VRAM に載っているか」を確認します。
モデルが降りていると、ロード時間が Cline の 30 秒予算に食い込んで失敗するためです。

ノートブックに実行履歴が残るので、**同じタスクを繰り返す運用**や
**手順を人に渡す**場面ではこちらが向いています。

### T3: VS Code 拡張のターミナル

手元の VS Code に `Google.colab` 拡張を入れ、Colab ランタイムに接続したうえで:

- コマンドパレット（`Ctrl/Cmd+Shift+P`）→ `Colab: Open Terminal`
- またはノートブック上部の *Colab* ボタン → *Open Terminal*

開いたターミナルは **Colab ランタイム上**なので、そこで `cline` を起動すれば
VM の Ollama にそのまま届きます。拡張の Contents view で `/content` のファイルも
VS Code 側から扱えます。

この機能は拡張側で「実験的」と位置づけられています。

## 5. モデル選定 — 判断基準が v1.0 から変わった

### 5.1 なぜ 7B を既定にしたか

v1.0（VS Code 拡張）では **14B** を推奨していました。拡張には Request Timeout の
設定項目があり、180 秒に伸ばせば大きいモデルの遅さを吸収できたからです。

**CLI にはそれがありません。** [cline#9182](https://github.com/cline/cline/issues/9182)
で報告されているとおり、Ollama へのリクエストは 30 秒で切られ、CLI 側に設定項目がありません。
報告者自身が「VS Code ではタイムアウトを設定すれば継続できる」と書いています。

したがって判断基準はこう変わります。

```
v1.0（拡張）: モデルの賢さ  >  速度      … タイムアウトは設定で伸ばせる
v2.0（CLI）:  prompt eval の速さ  >  賢さ  … 30 秒を超えたら何もできない
```

**30 秒で処理しきれないプロンプトは、賢いモデルでも 0 点です。**

### 5.2 T4 の制約（変わらず）

| 項目 | 値 | 影響 |
|---|---|---|
| VRAM | 16GB（実効 約 14.6GiB） | 重み + KV キャッシュ + 計算バッファ |
| Compute Capability | 7.5 (Turing) | **bf16 非対応** → vLLM 不利、Ollama (GGUF) 一択 |
| FlashAttention 2 | 非対応（sm_80 以上が必要） | 長コンテキストで不利 |
| メモリ帯域 | 約 320GB/s | 生成速度の律速 |

### 5.3 VRAM の成立表

KV バイト/トークン = `2(K,V) × 層数 × KVヘッド数 × head_dim × 精度バイト数`

| モデル | 層数 | KVヘッド | head_dim | KV/token (f16) |
|---|---:|---:|---:|---:|
| Qwen2.5-Coder-14B | 48 | 8 | 128 | 0.188 MiB |
| Qwen2.5-Coder-7B | 28 | 4 | 128 | 0.055 MiB |

`OLLAMA_KV_CACHE_TYPE=q8_0` で KV は約半分になります。

| モデル | 重み | num_ctx | KV(q8_0) | 合計＋バッファ | VRAM 判定 |
|---|---:|---:|---:|---:|:--:|
| 7B q4_K_M | 4.4 GiB | 32768 | 0.9 | **約 6.1 GiB** | ◎ |
| 7B q5_K_M | 5.1 GiB | 32768 | 0.9 | 約 6.8 GiB | ◎ |
| 14B q4_K_M | 8.4 GiB | 16384 | 1.5 | 約 10.8 GiB | ◎ |
| 14B q4_K_M | 8.4 GiB | 32768 | 3.0 | 約 12.5 GiB | ○ |
| 14B q4_K_M | 8.4 GiB | 65536 | 6.0 | 約 15.8 GiB | ✕ |
| Devstral 24B q4_K_M | 13.0 GiB | — | — | 重みだけで枠を使い切る | ✕ |
| Qwen3-Coder 30B-A3B q4_K_M | 17.7 GiB | — | — | 載らない | ✕ |

**VRAM は 14B でも載ります。問題は VRAM ではなく 30 秒の壁です。**

### 5.4 だから実測する

`20_ollama.sh` は約 4000 トークンのプロンプトを投げて prompt eval 速度を測り、
**30 秒で安全に処理できるプロンプト長**を逆算します。

```
      prompt eval        : 4000 tok / 2.2s = 1800 tok/s
      generation         : 16 tok / 0.4s = 40.0 tok/s

      Cline CLI の 1 リクエスト予算 : 30s
      うち prefill に使える目安     : 21s
      ★ 安全に投げられるプロンプト長 : 約 37,800 トークン

      判定: OK
```

| 判定 | 安全プロンプト長 | 意味 |
|---|---|---|
| OK | 12,000 以上 | そのまま進んでよい |
| WARN | 6,000〜12,000 | 動くが 1 ファイルずつの小さいタスクに限定する |
| NG | 6,000 未満 | Cline のシステムプロンプトだけで 30 秒を超える。実用にならない |

**この数字を見てからモデルを決めてください。** 表を眺めて決めるより確実です。

| 用途 | BASE_MODEL | NUM_CTX |
|---|---|---|
| 既定（tool-calling 実績あり） | `qwen3:8b` | 32768 |
| qwen2.5-coder 系を使う場合 | **§5.6 を読んでから。** 実タスクで完走するか要確認 |

`num_ctx` を 32768 より上げないこと。外挿になり品質が落ちます。

## 5.6 qwen2.5-coder:7b-instruct-q4_K_M は Cline から使えない（実機で確認）

**結論: 既定モデルを qwen2.5-coder:7b-instruct-q4_K_M から qwen3:8b に変更した。**
理由は速度でも VRAM でもなく、**Ollama の tool-calling に従わずファイルを一切
書けない**ため。V-2（実タスク完走）の検証で判明した。

### 症状

Cline に「fizzbuzz.py を作って」と頼むと、コードをチャットの中に
```python ... ```
として印字するだけで、実際のファイルは作られない。`cline -v` の詳細出力を見ると、
モデルは

```json
{"name": "editor", "arguments": {...}}
```

のような JSON を ```json フェンス付きでテキストとして返しており、
Cline 側のツール呼び出しとして解釈されていない。

### 原因（`ollama show cline-coder --template` で特定）

Ollama がこのモデルに適用するテンプレートは、tools が渡されたときに
次の指示をシステムプロンプトへ埋め込む。

```
For each function call, return a json object with function name and arguments
within <tool_call></tool_call> with NO other text. Do not include any
backticks or ```json.
<tool_call>
{"name": <function-name>, "arguments": <args-json-object>}
</tool_call>
```

qwen2.5-coder:7b-instruct-q4_K_M は、この `<tool_call>` ラッパーを付けずに
中身の JSON だけを返す。Ollama サーバ側のパーサーは `<tool_call>` タグの有無で
`message.tool_calls` を埋めるかどうかを決めているため、タグが無いと丸ごと
`message.content`（＝ただのテキスト）として返る。Cline はテキストをツール呼び出し
として実行しないので、何も起きない。

**実機で確認した再現条件（`/api/chat` に `tools` を渡して直接検証）:**

- 3 回連続で同じ失敗（`<tool_call>` タグ無し）
- `temperature: 0` でも同じ（ランダム性の問題ではない）
- システムプロンプトに `<tool_call>` の使用例を明示的に追加しても改善しない
- `/api/chat`（ネイティブ）と `/v1/chat/completions`（OpenAI 互換）の
  どちらでも同じ（エンドポイントの問題ではない）

対照実験として `qwen3:8b` に同じ `tools` を渡すと、2 回とも正しく
`message.tool_calls` が構造化されて返ってきた。Cline 経由の実タスク
（fizzbuzz.py の作成→実行）も qwen3:8b では完走する。

**ただし §5.7 のとおり、`<tool_call>` 自体は正しく返せても、
引数の中身（`editor` の `old_text`/`insert_line`）を安定して組み立てられる
とは限らない。** 「tool-calling プロトコルに従うか」と「実タスクが毎回
完走するか」は別の検証軸として扱うこと。

### 教訓

`ollama show <model>` の `Capabilities: tools` は「モデルカードに tools が
宣言されている」ことを示すだけで、**そのモデルが実際に Ollama の
tool-calling プロトコルへ確実に従うことを保証しない。** 特に量子化された
小型モデルでは、エージェント用途に投入する前に実タスクで検証すること
（V-2 はそのためにある）。qwen2.5-coder 系を使いたい場合は、より大きい
量子化（q8_0 / fp16）や非量子化版で同様の検証をしてから採用するのを勧める。

## 5.7 既定モデル（qwen3:8b）でも `editor` の引数エラーで無限ループに陥ることがある（実機で確認）

**結論: `<tool_call>` の形式そのものは守っていても、引数の中身を安定して
組み立てられるとは限らない。V-2（実タスク完走）は 1 回通ったからといって
毎回通るとは限らないので、`--retries` や `--timeout` を過信しないこと。**

### 症状

`bash scripts/50_run.sh "fizzbuzz.py を作って実行して"` を実行すると、
Cline が `editor` ツールを `old_text`/`insert_line` を指定せずに呼び、

```
error: {"error":"✖ Invalid input: expected string, received undefined\n  → at path"}
```

を受け取る。ここまでは単なる 1 回の失敗だが、**モデルはこのエラーを見て
「引数の形式を直そう」と考えた直後、全く同じ間違った形式で再度呼び直す。**
実機のログでは、この「同一の思考テキスト → 同一の誤った呼び出し →
同一のエラー」というサイクルが **一字一句そのまま 30 回以上** 繰り返され、
20 分近く止まらなかった（`fizzbuzz.py` の mtime は実行前後で一切変化せず、
ファイルは 1 度も書けていない）。

### `--timeout` / `--retries` は歯止めにならない

`cline --help` 上は次のどちらも「歯止め」に見えるが、**今回の実機では
どちらも機能しなかった。**

| フラグ | ヘルプの説明 | 実機での挙動 |
|---|---|---|
| `-t, --timeout <seconds>` | タスク全体のタイムアウト（既定 0 = 無制限）。`50_run.sh` は既定 `TASK_TIMEOUT=900`（15 分）を渡す | 900 秒を過ぎても止まらず、18 分超まで実行し続けた（外側から `kill` して初めて停止） |
| `--retries [value]` | 「連続ミス」の最大回数、これを超えたら終了（既定 6） | 同一エラーが 30 回連続しても終了しなかった。「引数エラーで即リトライ」は `--retries` が数える「ミス」に計上されていない可能性がある |

したがって **セルやスクリプトから自動実行する場合は、`50_run.sh` /
`cline` 自身の歯止めをあてにせず、外側で `timeout` コマンドを併用するか、
無応答が続いていないかを別途監視すること。**

### 対策（効く順）

| # | 対策 | 効果 |
|---|---|---|
| 1 | タスクを「1 ファイル・1 変更」まで小さく切る | エラーが起きる余地そのものを減らす |
| 2 | `.cline/rules/` に「`editor` は必ず `old_text` と `new_text` の両方を指定する」等、ツール引数の具体例を明示する | モデルが正しい形式を思い出しやすくなる（未検証・試す価値あり） |
| 3 | 長時間無応答なら手動 `kill` する前提で運用する | `--timeout`/`--retries` を信用しない |
| 4 | 一度失敗したら同じプロンプトで再試行する（プロンプトキャッシュが効くため 2 回目は速い。§7 補足） | 1 回目のループにたまたま入っただけの可能性がある |

## 5.8 qwen2.5-coder:14b-instruct-q4_K_M + Codex CLI — 同じ不具合をプロキシで修復する（実機で確認）

**結論: 14b でも §5.6 と同根の不具合が再現する（生 JSON が `content` に落ちる）。
モデルやプロンプトを変えるのではなく、Ollama と Codex の間に修復プロキシ
（`scripts/32_codex_tool_proxy.py`）を挟むことで、`tool_calls` を正しく
組み替えて Codex から実際にツールを実行できるようにした。**
既定で有効（`CODEX_TOOL_REPAIR=1`）。参考: 本節末尾の外部記事・issue。

### 症状（再現条件は §5.6 と同一）

`BASE_MODEL=qwen2.5-coder:14b-instruct-q4_K_M` で `--with-codex` を実行し、
Codex CLI から実タスク（例: `codex exec "fizzbuzz.py を作って実行して"`）を
投げると、Codex はモデルの応答をそのままテキストとしてチャットに表示するだけで、
ツールを一切実行しない。`/v1/chat/completions` や `/v1/responses` に `tools`
を渡して直接叩くと、`message.content`（または Responses API の
`output[].content[].text`）に

```json
{"name": "shell", "arguments": {"command": ["ls"]}}
```

のような生 JSON がそのまま返り、構造化された `tool_calls` / `function_call`
は空。openai/codex#2229 で報告されているのとまったく同じ症状で、同 issue 内の
コメント（BigMitchGit 氏）も「Ollama 側がテンプレート通りの構造化出力を
返せていないだけで、Codex の問題ではない」と結論づけている。

### 原因

§5.6 と同じ：Ollama のテンプレートは `<tool_call>{...}</tool_call>` で囲むよう
指示するが、qwen2.5-coder はサイズ（7b/14b）によらずこのラッパーを付けない
ことがある。Ollama サーバのパーサーは `<tool_call>` タグの有無だけで構造化出力を
埋めるかどうかを決めているため、タグが無いと丸ごとプレーンテキストとして返る。
`/v1/chat/completions` と `/v1/responses` のどちらでも実機で同一の壊れ方を確認した。

### Codex CLI 0.15x 系は `wire_api = "chat"` を廃止している（新事実）

本節を実装する過程で判明した追加の事実: Codex CLI 0.154.0 は起動時に

```
Error loading config.toml: `wire_api = "chat"` is no longer supported.
How to fix: set `wire_api = "responses"` in your provider config.
```

で止まり、**カスタムプロバイダで `wire_api = "chat"` を選ぶこと自体ができない。**
そのため修復プロキシは `/v1/chat/completions`（aider 等 Chat Completions 系
クライアント向けに残してある）に加えて **`/v1/responses`（Responses API）を
主目的として実装している。** `CODEX_TOOL_REPAIR=1`（既定）のときは
`wire_api = "responses"` に固定してプロキシへ向ける。

### 解決策: 修復プロキシ

「モデルを変える」以外の選択肢として、Codex と Ollama の間に立って
レスポンスを検査し、プレーンテキストに埋もれたツール呼び出し JSON を
正しい構造（Responses API なら `function_call` item、Chat Completions なら
`tool_calls`）に組み替える透過プロキシを追加した
（`scripts/32_codex_tool_proxy.py`、Python 標準ライブラリのみ）。

- `<tool_call>` タグ付き / ```` ```json ```` フェンス付き / 素の JSON の
  いずれの形でも、リクエストで渡された `tools` の名前と一致する
  `{"name":..., "arguments":...}` を見つければ組み替える
- **名前が一致しなければ何もしない**（本物のテキスト回答を壊さない、かつ
  存在しないツール名への誤った書き換えを防ぐ。次項参照）
- ストリーミング要求には、修復後の内容を最小限の SSE イベント列にまとめて
  返す（**トークンの逐次表示は失われる**。正しさを優先するトレードオフ）

```bash
# 既定（プロキシ経由。qwen2.5-coder 系の不具合を吸収する）
BASE_MODEL=qwen2.5-coder:14b-instruct-q4_K_M NUM_CTX=16384 \
  bash scripts/00_setup_all.sh --with-codex

# プロキシを無効化して素の挙動を見る（デバッグ用）
CODEX_TOOL_REPAIR=0 bash scripts/31_alt_agents.sh codex
```

### 実機での検証結果

1. **プロキシ無効（直結）**: `codex exec "fizzbuzz.py を作って実行して"` を
   投げると、Codex は `{"name": "exec_command", ...}` 等の JSON をチャットに
   印字するだけで、`fizzbuzz.py` は一度も作られなかった（`wire_api="chat"`は
   Codex 起動時に拒否されるため `wire_api="responses"` 直結で再現）。
2. **プロキシ有効**: 同じプロンプトで、プロキシのログに
   `POST /v1/responses -> repaired` が記録され、Codex 側は実際に
   `exec_command` をルータへ渡すところまで進んだ（このモデル・バージョンの
   組み合わせでは、その先で Codex 0.154 の `exec_command` が要求する
   `sandbox_permissions` 引数をモデルが省略し、`approval_policy = "never"`
   のため拒否される、という**別の**（プロトコル不一致ではなく引数構築の
   信頼性の）問題に当たった。§5.7 と同種の問題であり、本プロキシの対象外）。
3. より単純なタスク（`シェルコマンドで echo hello world > hello.txt を実行して`）
   ではプロキシ経由で `exec_command` が正しい引数で呼ばれ、実際に
   `hello.txt` が作成されるところまで実機で確認できた。

**教訓（§5.7 と同じ整理）**: 修復プロキシが解決するのは「ツール呼び出しの
JSON が構造化フィールドに正しく載るか」という **プロトコル互換性の問題**
までであり、「モデルが正しいツール名・正しい引数を毎回組み立てられるか」
という **タスク完走の信頼性の問題** は別軸のまま残る。14b 量子化モデルは
後者で `shell` を `Run` と呼んだり `exec_command` を `apply_patch` と
呼んだりする揺らぎが実機で観測されており、これはプロキシ側で安全に
（誤爆させずに）矯正できる種類の誤りではない。

詳細な検証ログは本ブランチの `RESULT.md` を参照。

### 5.8.1 追加の実機不具合: ファイルは作るが中身が空になる

**症状**: `codex exec` / 対話セッションで複数ファイルの実装（例:
`json_parser.py` + `test_json_parser.py` を作って）を頼むと、両ファイルとも
作成はされる（`ls` に出る）が **中身が 0 バイト**。一方でチャットの応答には
完成したコードがベタ書きのテキストとして出力されている。

proxy ログでは次のパターンが交互に現れる:

```
POST /v1/responses -> repaired    (tools=7, ...)   # ファイル作成系ツール呼び出しあり
POST /v1/responses -> passthrough (tools=0, ...)   # ツール呼び出し無し。プレーンテキスト応答
```

**原因**: モデルがファイル作成ツール（`apply_patch` 等）を **`content` 引数を
空/省略したまま** 呼び出し、本来そこに書くはずだったコードを別途チャットの
説明テキストとして出力してしまう。修復プロキシは `tool_calls` の構造（JSON の
組み替え）は直せるが、モデルが渡してきた引数の中身までは補完できないため、
これはプロキシの対象外。5.8 本文で述べた「タスク完走の信頼性の問題」の
具体例であり、`shell`/`Run` の呼び間違いと同根（モデルが「ツールを呼ぶこと」
と「コードを書くこと」を別々のアクションだと誤解している）。

**回避策**:
- コードはチャット応答に残っているので失われてはいない。手作業で
  該当ファイルにコピーすれば完了できる。
- 指示に「チャットに貼らず、ツールで直接ファイルへ反映し、書き込み後に
  `cat` で中身が空でないことを自分で確認してから完了報告して」という一文を
  足すと、空ファイルのまま完了報告するのを多少抑制できる（根本解決ではない）。
- 複数ファイルを同時に頼むと崩れやすいので、1 ファイルずつ依頼する。
- 頻発する場合は、より指示追従性の高いモデルへの切り替えを検討する。

## 5.9 AGENTS.md でローカルモデル運用ルールを常設する

§5.8.1 の「ファイルは作るが中身が空になる」不具合は、`apply_patch` の
unified diff をやめて **shell ツール（exec_command）で heredoc を使い、
ファイル全体を書き直させる** よう明示的に指示すると回避できることを実機で
確認した。ただし毎回プロンプトに書くのは非現実的なので、Codex CLI の
[AGENTS.md](https://developers.openai.com/codex/guides/agents-md) に焼き込んで
常設する。

Codex CLI はワークスペースの git root から `AGENTS.md` を毎ターン読み込み、
プロンプトの先頭に自動で足す（Cline CLI の `.cline/rules/*.md` と同じ発想の
公式機能）。`31_alt_agents.sh codex` はこれを利用して、実行のたびに
`$WORKSPACE/AGENTS.md` へ次の内容を書き出す（常に上書き。手で調整したい
場合は同スクリプトの当該ヒアドキュメントを直接編集する）:

- `apply_patch` を使わず、`cat > file << 'EOF' ... EOF` の heredoc で
  ファイル全体を書き直すこと
- 説明文だけを書いて終わらず、先にツールを呼び出すこと
- 書き込み後は `ls -la` / `cat` で中身が空でないか自分で確認してから
  完了報告すること
- 複数ファイルは同時に頼まず 1 ファイルずつ進めること

適用箇所: `scripts/31_alt_agents.sh` の `[ "$WHICH" = "all" ] || [ "$WHICH" = "codex" ]`
ブロック内、`config.toml` 書き出し直後。

### さらに踏み込むなら: model-catalogs（未検証・上級者向け）

Codex CLI の `config.toml` には `model_catalog_json` というキーがあり、
モデルごとのメタデータを JSON ファイルで定義してモデル名に紐づけ、自動適用
できるらしい（キー自体は公式の advanced config ドキュメントに記載がある）。
うまく使えば、モデルごとの既定指示文や `apply_patch` の扱いを個別に制御でき、
`cline-coder` 実行時に出る「Model metadata for cline-coder not found」の
警告も消せる可能性がある。

## 5.10 gemma4:12b-it-qat（Gemma 4 12B QAT）— 一度却下した Gemma を再評価する

### 経緯: Gemma 3 は却下していた

`docs/リモート化計画.md` §0.3 で、Gemma は明示的に評価対象から外していた。
理由は **「Gemma 3 は Ollama のテンプレートに tool calling が入っていない」**
（capabilities に `tools` が無い）で、これは §5.6 で
`qwen2.5-coder:7b-instruct-q4_K_M` が落ちたのとまったく同じ罠だった。

**Gemma 4 ではこの前提が変わった。**

| 項目 | 値 |
|---|---|
| Ollama タグ | `gemma4:12b-it-qat` |
| サイズ | **重み 6653 MiB = 6.50 GiB**（実測。Google が QAT した q4_0） |
| capabilities | vision / **tools** / thinking / audio |
| 構成 | 11.95B params / 48 層 / 256K ctx / Dual Attention（局所 1024 と大域の交互、最終層は大域） |
| 公開 | 2026-06-03 / Apache 2.0 |

### VRAM: num_ctx は 32768 にできる（2026-09-18 実測）

レジストリのマニフェストから重みを実測したところ、
**`image.model` 6653 MiB + `image.projector` 167 MiB = 6820 MiB (6.66 GiB)** だった
（ollama.com の表示「約 7.2GB」は 10 進の GB）。
**projector はマルチモーダルの投影層で、これもメモリに載る。**
`vram_precheck.py` は `image.model` しか数えておらず 167 MiB 過小だったので直した。
T4 の空き 14913 MiB に対して:

| num_ctx | KV 見積り | 余裕 | 判定 |
|---:|---:|---:|:--:|
| 32768 | 0.0078（頭打ちあり） | +7198 MiB | OK |
| **32768** | **0.164（頭打ちなし・安全側）** | **+2079 MiB** | **OK** |
| 65536 | 0.164（頭打ちなし） | -3295 MiB | NG |

（頭打ちありの行は、これとは別に SWA の固定分 約 160 MiB がかかる。
`vram_precheck.py` は「1 トークンあたり」の平坦なモデルしか持たないので、
固定分は表現できていない。安全側の 0.164 で運用するぶんには問題にならない。）

**KV の実寸は確定した**（GGUF メタデータより。`scripts/36_registry_probe.py`）:

| 項目 | 値 |
|---|---|
| 層 | 48 = SWA 40 + 大域 8（SWA×5 + 大域×1 の繰り返し） |
| KV ヘッド | SWA 層 8 / **大域層 1** |
| key/value 長 | 大域 512/512 / SWA 256/256 |
| sliding window | 1024 |

ただし**答えが 2 通りに割れる**。Ollama が SWA 層の KV を window で頭打ちに
するかどうかで、必要量が一桁変わる:

| | q8_0 | ctx=32768 の KV |
|---|---|---:|
| 頭打ち**あり** | 0.0078 MiB/tok + 固定 160 MiB | 416 MiB |
| 頭打ち**なし** | 0.164 MiB/tok | 5,374 MiB |

どちらかは実機で測るまで分からないので、`KV_MIB_PER_TOKEN` には
**安全側（頭打ちなし = 0.164）**を置いてある。当初の 0.05 は、頭打ちが
無かった場合に 3 倍以上楽観で、**載らないものを OK と誤判定する向き**に外れていた。

32768 はその安全側でも +2079 MiB 残る（projector 込み）ので採用。
頭打ちがあると分かれば 131072 でも載る計算になる。

§5.3 と `20_ollama.sh` が言うとおり「`num_ctx` が 32768 未満だと Cline は
まともに動かない」ので、載るなら 16384 に落とす理由が無い。

### ★ ただし capabilities は今回も保証にならない

Gemma 4 には **「tool_calls に入らず content に漏れる」不具合が 2 系統**
報告されている。§5.6 / §5.8 / §12.7 でこのリポジトリが 3 回踏んだのと同じクラスである。

**(1) [ollama/ollama#15539](https://github.com/ollama/ollama/issues/15539)**

**修復コードを先に書かない。** まず実挙動の証拠を採る:

- `_find_gemma_wrapped_tool_calls()` — (1) のラッパー形を展開する。

### ★ 訂正 (2026-09-18): (2) の実装は外れていた — テンプレート実物で確認した

当初 (2) は **issue の文章から起こして**実装し、「逐語のサンプルが無い」と明記していた。
その後 `scripts/36_registry_probe.py` で **モデルのチャットテンプレート実物**
（GGUF の `tokenizer.chat_template`、17,466 文字）を読んだところ、**外れていた**。
pull は不要で、レジストリのブロブ先頭を `Range` で 96 MiB 取るだけで読める。

テンプレートが tool call を吐くのはここだけ:

```jinja
{{- '<|tool_call>call:' + function['name'] + '{' -}}
    {%- for key, value in function['arguments'] | dictsort -%}
        {{- key -}}:{{- format_argument(value, escape_keys=False) -}}
    {%- endfor -%}
{{- '}<tool_call|>' -}}
```

`format_argument` は文字列を `<|"|>` で囲む。実際の出力は:

```
<|tool_call>call:write_file{content:<|"|>hi<|"|>,path:<|"|>hello.txt<|"|>}<tool_call|>
```

外していた点:

| # | 当初の実装 | 実際 |
|---|---|---|
| 1 | `<\|tool_call\|>`（左右対称） | `<\|tool_call>` … `<tool_call\|>`（**非対称**。対称形は実在しない） |
| 2 | `call:` が行頭に単独で出る | `<\|tool_call>call:` と地続き |
| 3 | `<\|"\|>` を `"` に置換すれば JSON | **キーが裸**なので JSON にならない |

3 が本質的で、正規表現の置換では原理的に読めない。`_gemma_parse_value()` /
`_find_gemma_native_tool_calls()` を足し、テンプレートの `format_argument` と
同じ文法（裸キー / `<|"|>` 文字列 / `true`,`false` / 数値 / 入れ子の写像・配列）を
再帰で読むようにした。素朴に `}` を探すと文字列中の `,` `}` で壊れるので、
閉じ `<|"|>` まで読む。

テンプレートに現れるトークンの全体:

```
<|tool_call>  … <tool_call|>        <|tool_response> … <tool_response|>
<|channel>    … <channel|>          <|turn>          … <turn|>
<|tool>       … <tool|>
<|"|>  <|think|>  <|image|>  <|audio|>  <|video|>      （これらは対称）
```

> **これは「テンプレートがそう書けている」という根拠であって、実出力そのものでは
> ない。** モデルはこの形式で訓練されているので同じ形を吐く公算が高いが、
> Ollama のパーサが `tool_calls` に入れられるかを含め、確認は実機
> （`scripts/34_toolcall_probe.sh`）で行う。
>
> (1) は issue 本文の逐語サンプルをそのまま使っている。

### 未確定事項

  大域 attention を交互に使うため、既存プロファイルの

### 6.2 設定コマンド

**CLI 3.x では `cline config set key=value` は廃止されている**
（`error: too many arguments. Expected 1 argument but got 2.`）。
Plan/Act で別プロバイダを持つ概念も無くなり、`cline auth` で現在のプロバイダを

TTY が無いここでは `error: interactive mode requires a TTY` で必ず失敗するので、
非対話での確認は `providers.json` を直接読む（`30_cline_cli.sh` / `90_healthcheck.sh`

**キー名・サブコマンドは CLI のバージョンで変わりえます。** 反映されているか
不安なら、ターミナル（TTY）から対話設定を使ってください。

```bash

```

## 7. Ollama リクエストのタイムアウト

> ## ★ 訂正 (2026-09-18): 30 秒ではなくなっている
>
> **この節が長らく「最大の壁」として扱ってきた 30 秒制限は、Cline CLI 3.0.62 では
> 起きない。実測で確認した（`scripts/35_cline_timeout_probe.sh`）。**
>
> | 上流の応答時間 | プロバイダ | 結果 |
> |---:|---|---|
> | 45s | `ollama` / `openai-compatible` | どちらも完走 (exit 0) |
> | 120s | `ollama` / `openai-compatible` | どちらも完走 (exit 0) |
> | 340s | `ollama` | **302s で中断** — `Ollama request timed out after 300 seconds` |
>
> 仕組み自体（`AbortController` で中断する）は残っているが、**既定値が 30 秒から
> 300 秒に上がっている**。実装にも該当の定数がある:
>
> ```
> @cline/llms/dist/providers.js   OLLAMA_DEFAULT_TIMEOUT_MS = 300000
> @cline/llms/dist/index.js       同上
> ```
>
> さらに、この値はプロバイダ設定の `timeoutMs` で上書きできる実装になっている
> （`O0(e)` が `e.timeoutMs` を読み、無ければ既定値を使う）。したがって
> **「CLI 側に設定項目が無い」という記述も、もう正確ではない。**
>
> ### 何が変わるか
>
> - **Cline CLI を避ける理由としての「30 秒」は無くなった。** Codex CLI を
>   選ぶ理由が「タイムアウトを設定できるから」だけなら、その前提は崩れている
>   （§7.1 の比較表も、この観点では読み替えが必要）
> - **T4 なら 300 秒はほぼ制約にならない。** §5.4 の実測（prefill 854 tok/s /
>   generation 32.2 tok/s）なら、300 秒は出力 2000 トークンでも十分収まる
> - **CPU では逆に 300 秒でも足りない可能性がある。** 12B 級を CPU で回すと
>   prefill だけで数分かかる。そのための引き上げ用スクリプトが
>   `scripts/33_patch_cline_timeout.sh`（§13）
>
> ### 未検証だった V-4 の結論
>
> 対策 6 番「`CLINE_PROVIDER=openai-compatible` なら 30 秒制限を回避できる可能性」は
> **検証済み・意味を失った**。120 秒の遅延に対して両プロバイダとも完走しており、
> 差は観測されなかった。そもそも回避すべき 30 秒が存在しない。
>
> ### Codex CLI 側は 300 秒ではなく「イベント間の間隔」で切る（2026-09-18 実測）

Codex CLI 0.155.1 を `scripts/37_codex_timeout_probe.sh` で測った。
`config.toml` の `stream_idle_timeout_ms` は**認識される**（バイナリの設定
フィールドに存在）が、**何を縛るのかが直感と違う**。

上流の沈黙 60 秒・`stream_idle_timeout_ms = 30000`（30 秒）で固定し、
沈黙のさせ方と経路だけを変えた:

| 経路 | 沈黙のさせ方 | 経過 | 結果 |
|---|---|---:|---|
| 直結 | 最初の 1 バイトまで 60s（`ttfb`） | 61s | **完走** |
| 直結 | 最初のイベントは即返し、その後 60s（`gap`） | **30s** | **中断** `idle timeout waiting for SSE` |
| プロキシ | `ttfb` | 60s | 完走 |
| プロキシ | `gap` | 61s | **完走** |

**読み方:**

1. **`stream_idle_timeout_ms` は初回バイトまでの時間を縛らない。**
   縛るのは **SSE イベントとイベントの間隔**だけ。
   prefill が何分かかっても、この設定では切られない。
2. **修復プロキシを噛ませると、Codex は idle timeout にかからなくなる。**
   プロキシは上流へ `stream:false` で投げ、応答が揃ってから
   1 チャンクにまとめて返す（§5.8）。イベント間の間隔が生じないので、
   構造上 idle timeout が発火しえない。
   代償はストリーミング表示が失われること。既知の副作用だったが、
   **タイムアウトの意味まで変えている**ことは今回まで気付いていなかった。

つまり実運用では:

- **直結**なら、生成中にトークンが途切れる（CPU で極端に遅い等）と切られる
- **プロキシ経由**なら、どれだけ遅くても切られない代わりに、
  完了まで画面が動かない

### 測り方（モデル不要・GPU 不要）
>
> ```bash
> PROBE_DELAY_SEC=340 bash scripts/35_cline_timeout_probe.sh   # Cline
> PROBE_STALL=gap bash scripts/37_codex_timeout_probe.sh        # Codex
> ```
>
> 遅延を秒単位で指定できるスタブ上流（`scripts/test_slow_upstream_stub.py`）を
> 立てて測る。実モデルより正確で速い。境界を狙って作れるし、モデルの
> 出来不出来が混入しない。
>
> スタブは沈黙のさせ方を 2 通り作り分けられる（`STUB_STALL_MODE`）。
> `ttfb` は最初の 1 バイトまで沈黙、`gap` は最初のイベントを返してから沈黙。
> **この 2 つを撃ち分けないと、クライアントの「idle timeout」が
> 初回バイトまでを縛るのかイベント間を縛るのかが分からない。**
>
> **以下は 30 秒制限が存在した時期の記述である。** 古い Cline CLI を使う場合や、
> `timeoutMs` を明示的に短くした場合には今も当てはまる。対策 1〜5 は
> タイムアウトの有無にかかわらず「CPU/GPU 予算を節約する」策として有効なので
> 残してある。

### 症状（30 秒時代）

```
Ollama request timed out after 30 seconds
（3 回リトライして停止）
```

### 原因

Cline CLI の Ollama ハンドラに 30 秒のタイムアウトが埋まっており、
**CLI 側に設定項目がありません**（[cline#9182](https://github.com/cline/cline/issues/9182)、
2026-09 時点で未解決）。VS Code 拡張には Request Timeout の設定があるため、
「拡張では動くのに CLI では動かない」という形で現れます。

Cline は毎リクエストで「システムプロンプト + 環境情報 + ディレクトリ構造 +
ファイル内容 + 会話履歴」を送ります。T4 の prompt eval 速度でこれを 30 秒で
処理しきれないと、生成が始まる前に切られます。

### 対策（効く順）

| # | 対策 | 効果 |
|---|---|---|
| 1 | **モデルを小さくする** | 最も確実。prefill 速度がそのまま効く |
| 2 | **タスクを小さく切る** | Cline が読むファイルが減り、プロンプトが縮む。`.cline/rules/` で誘導する |
| 3 | **`OLLAMA_KEEP_ALIVE=-1`** | モデルのロード時間が 30 秒予算に食い込むのを防ぐ。`common.sh` で設定済み |
| 4 | **`num_ctx` を下げる** | 上限が下がるので Cline が長い文脈を作りにくくなる |
| 5 | **会話が伸びたら新しいタスクを始める** | 履歴が prefill を押し上げる。プロンプトキャッシュが効かない場面で特に重要 |
| 6 | **`CLINE_PROVIDER=openai-compatible`** | ~~`/v1` 経由にして Ollama 専用ハンドラを迂回する。**未検証（V-4）**~~ → **2026-09-18 検証済み。両プロバイダで差は無く、そもそも回避すべき 30 秒が存在しない（上の訂正を参照）** |
| 7 | **別の CLI エージェントに替える** | ~~**タイムアウトを設定できるものがある。**~~ → 3.0.62 では Cline も 300 秒。§7.1 |

### 6 番について

Ollama は `/v1/chat/completions` で OpenAI 互換 API を出しています。
Cline の OpenAI プロバイダ経由にすれば、Ollama ハンドラの 30 秒制限を
迂回できる可能性があります。

```bash
CLINE_PROVIDER=openai-compatible bash scripts/30_cline_cli.sh
```

ただし Cline 側のタイムアウトがプロバイダ共通の実装だった場合は効きません。
**実機で確かめてください。効くなら 14B が実用圏に入ります。**

### 補足: プロンプトキャッシュ

Ollama は直前のプロンプトと共通する接頭辞を再利用します。
そのため **危ないのはタスクの 1 回目**で、2 回目以降は差分だけの処理になり速くなります。
「最初の 1 回だけ落ちる」なら、この対策で抜けられることが多いです。

## 7.1 タイムアウトは Cline 固有の問題 — 他の CLI エージェントとの比較

30 秒の壁は Cline CLI の実装上の制約であって、ローカル LLM 全般の宿命ではありません。
**設定で伸ばせるエージェントがあります。**

| エージェント | タイムアウト設定 | 単位・既定 | 性格 | 評価 |
|---|---|---|---|:--:|
| **Codex CLI** | `stream_idle_timeout_ms` + `request_max_retries` / `stream_max_retries` | ms | **自律エージェント（Cline に最も近い）** | ◎ |
| **Qwen Code** | `generationConfig.timeout`（settings.json） | ms / **ローカルには 300000 を推奨と明記** | 自律エージェント寄り | ◎ |
| **aider** | `--timeout` / 環境変数 `AIDER_TIMEOUT` | 秒 / **既定 None（無制限）** | ペアプログラマ型 | ◎ |
| **Goose** | `GOOSE_TIMEOUT` は接続のみ。ストリームには別途 `GOOSE_STREAM_TIMEOUT` が必要 | 秒 | 自律エージェント | △ |
| **opencode** | `options.timeout` を入れても効かない報告。加えてローカル時に +75 秒の内部オーバーヘッド | — | 自律エージェント | ✕ |
| **Cline CLI** | **無し** | — | 自律エージェント | ✕ |
| Cline VS Code 拡張 | Request Timeout（設定 UI にある） | ms / 既定 30000 | 自律エージェント | ◎ |

補足:

- **Cline CLI の状況は最新版でも変わっていません。** [#9484](https://github.com/cline/cline/issues/9484)（v2.4.2）は
  [#9328](https://github.com/cline/cline/issues/9328) の重複として閉じられ、
  「設定は全プラグイン種別で揃うべきだが CLI が拡張に追いついていない」と整理されています。
  拡張側は [#2941](https://github.com/cline/cline/issues/2941) 経由でタイムアウト設定が入りました。
- **Cline にはもう 1 段のタイムアウトがあります。** [#6549](https://github.com/cline/cline/issues/6549)（P1・未解決）は、
  Node の undici の既定 `headersTimeout`（約 300 秒）により、**prefill が長いリクエストが
  Ollama 側の設定に関係なく切られる**問題です。30 秒を回避できても、この 300 秒が次の壁になります。
- **Goose にも同種の罠があります。** [#8437](https://github.com/aaif-goose/goose/issues/8437) は
  `GOOSE_TIMEOUT: 1200` を設定しても "Ollama stream stalled: no data received for 30s" で落ちるという報告で、
  未文書の `GOOSE_STREAM_TIMEOUT` を別に設定する必要があります。
- **opencode はローカルモデルに現状薦めにくい**です。
  [#18428](https://github.com/anomalyco/opencode/issues/18428)（"hi" だけのプロンプトに 60〜90 秒、直接叩けば 3 秒）は
  closed as not planned になっています。

### 選ぶ軸は「1 ターンに送るプロンプト量」

T4 では prefill が律速なので、**エージェントが毎回どれだけ送るか**がそのまま実用性になります。

```
送る量: aider  <  Qwen Code  <  Codex CLI ≒ Cline
速さ  : aider  >  Qwen Code  >  Codex CLI ≒ Cline
自律性: aider  <  Qwen Code  <  Codex CLI ≒ Cline
```

**「Cline に近い」ことは、この構成では長所であると同時に短所です。**
Codex はタイムアウトの問題は解決しますが、**遅さの問題は解決しません。**
むしろ Cline と同じ理由で重い。

### Codex CLI — Cline に一番近い

自律エージェントらしさが要るなら第一候補です。Ollama 側も公式に統合ガイドを出しています。

```toml
# ~/.codex/config.toml
model = "cline-coder"
model_provider = "ollama-local"
model_context_window = 32768
model_max_output_tokens = 8192
sandbox_mode = "danger-full-access"
approval_policy = "never"

[model_providers.ollama-local]      # ★ "ollama" は予約済み。使えない
name = "Ollama (local)"
base_url = "http://127.0.0.1:11434/v1"
wire_api = "responses"               # ★ Codex 0.15x 系は "chat" を受け付けない（後述）
request_max_retries = 2
stream_max_retries = 5
stream_idle_timeout_ms = 600000   # ★ Cline CLI に無い設定
```

`stream_idle_timeout_ms` は「無通信のまま何 ms 待つか」です。
prefill 中は何も返ってこないので、**prefill の長さがここに効きます。**

**プロバイダ ID に `ollama` は使えません。** Codex CLI 0.153 以降は `ollama` を組み込みプロバイダとして
予約しており、`[model_providers.ollama]` を書くと起動時に

```
Error loading config.toml: model_providers contains reserved built-in provider IDs: `ollama`.
Built-in providers cannot be overridden. Rename your custom provider (for example, `openai-custom`).
```

で止まります。**`ollama-local` のように別名にしてください**（`model_provider` 側も同じ名前に）。
古い記事や Ollama 公式の統合ガイドは `ollama` のまま書いているので、コピーする際は必ず読み替えます。

`wire_api` は Ollama の版によって `/v1/responses` が生えているかどうかが違うので、
`31_alt_agents.sh` は `CODEX_TOOL_REPAIR=0` のとき `/v1/responses` を叩いて
`responses` / `chat` を自動判定します。**ただし Codex CLI 0.154.0 以降は
`wire_api = "chat"` 自体を起動時に拒否する**
（`` `wire_api = "chat"` is no longer supported. `` エラー、実機で確認済み）ため、
手で書くなら `responses` にしてください。`CODEX_TOOL_REPAIR=1`（既定）のときは
修復プロキシが `/v1/responses` を実装しているので、常に `responses` に固定されます
（§5.8）。

**Colab で使うときの注意が 3 つあります。**

1. **サンドボックスを切る必要があります。** Codex は Linux で seccomp/landlock を使いますが、
   コンテナ内では動かないことが多く（[codex#1039](https://github.com/openai/codex/issues/1039)）、
   "The combination of seccomp/landlock that Codex uses for sandboxing is not supported in
   this environment" で止まります。Codex 公式ドキュメントも
   「コンテナが境界ならサンドボックスを二重にするな」として `--sandbox danger-full-access` を案内しています。
   Colab の使い捨て VM なら許容できますが、**手元のマシンで同じ設定にしてはいけません。**
2. **コンテキストの要求が大きい。** Ollama の公式ガイドは Codex に
   「少なくとも 64k」を推奨しています。T4 で 64k を確保できるのは 7B までで
   （14B は KV が乗らない・§5.3）、しかも Qwen2.5-Coder のネイティブ長は 32k です。
   **推奨値を下回った状態で使うことになります。**
3. **ネイティブ tool calling が要ります。** Cline はプロンプト内の XML でツールを表現するので
   モデルを選びませんが、Codex は function calling 前提です。
   Ollama 側のテンプレートが対応している必要があります
   （`qwen2.5-coder` は対応済み。`ollama show <model>` の Capabilities に `tools` が出るか確認）。
   ただし **`Capabilities: tools` は宣言に過ぎず、実際に Ollama の `<tool_call>`
   ラッパー要求へ確実に従う保証は無い**（§5.6・§5.8）。qwen2.5-coder は 7b/14b
   いずれも生 JSON をプレーンテキストで返すことがあり、既定では
   `CODEX_TOOL_REPAIR=1` の修復プロキシがこれを吸収する（§5.8）。

`wire_api` は Ollama のバージョンで変わります。0.13.3 以降は `/v1/responses` を出すので
`"responses"`、それ以前は `"chat"`。`CODEX_TOOL_REPAIR=0` のとき `31_alt_agents.sh`
は実際に叩いて自動判定しますが、**Codex CLI 0.154.0 以降は `wire_api = "chat"`
自体を起動時に拒否する**ため、旧い Ollama で `chat` しか無い環境では Codex が
使えません。`CODEX_TOOL_REPAIR=1`（既定）の場合はプロキシが `/v1/responses` を
実装しているので、自動判定はスキップして `"responses"` に固定します（§5.8）。

### aider — 速さで選ぶなら

**タイムアウト設定があるからだけではありません。プロンプトが小さいことのほうが重要です。**
Ollama 対応も最も枯れており、`num_ctx` の扱いが公式ドキュメントに書かれています。

```bash
export OLLAMA_API_BASE=http://127.0.0.1:11434
aider --model ollama/cline-coder --timeout 600
```

```yaml
# .aider.model.settings.yml
- name: ollama/cline-coder
  extra_params:
    num_ctx: 32768
```

代償は自律性です。ファイルをコンテキストに追加して差分を作らせる使い方が中心で、
「自分でコマンドを実行し、結果を見て次を決める」度合いは低い。

### 使い分けの目安

`20_ollama.sh` のベンチ判定で決めるのが確実です。

| ベンチ判定（安全プロンプト長） | 薦める順 |
|---|---|
| OK（20,000 以上） | **Codex CLI** → Qwen Code → aider |
| OK（12,000〜20,000） | Qwen Code → Codex CLI → aider |
| WARN（6,000〜12,000） | **aider** 一択。自律エージェントは重すぎる |
| NG（6,000 未満） | エージェント以前の問題。モデルを小さくする |

### ただし、これは対症療法です

タイムアウトを伸ばしても、**30 秒待っていたものが 600 秒待てるようになるだけ**で、
体感は良くなりません。1 ターンに 5 分かかるエージェントは実用的とは言えません。

本命は §7 の対策 1〜5、つまり **prefill を速くすること**です。
ベンチ判定が NG なら、エージェントを替えても解決しません。

`scripts/31_alt_agents.sh` で Codex CLI / aider / Qwen Code を導入し、Ollama に向けられます。

```bash
bash scripts/31_alt_agents.sh          # 全部
bash scripts/31_alt_agents.sh codex    # Codex CLI だけ
```

## 7.2 Cline CLI 3.x は日本語プロンプトをコマンドライン引数で渡すと落ちる（実機で確認）

**症状:** `cline "fizzbuzz.py を作って"` のように日本語（非 ASCII 文字）を含む
プロンプトを**コマンドライン引数として**渡すと、必ず次のエラーで失敗する。

```
error: Unknown command or unquoted prompt: fizzbuzz.py を作って
Prompt text must be passed as a single quoted argument, for example: cline "fix the tests".
```

**再現条件（実機で確認済み）:**

- 日本語 1 文字（例: `cline "何"`）だけでも発生する
- ASCII と日本語が混ざっているだけでも発生する（例: `cline "a何"`）
- `--cwd` や `--timeout` の有無に関係なく発生する
- 純粋な ASCII プロンプト（例: `cline "say hello"`）は問題なく通る

このリポジトリの手順書・スクリプトは全面的に日本語プロンプトを想定しているため、
このバグは無視できない。

**回避策: プロンプトを引数ではなく標準入力で渡す。**

```bash
echo "fizzbuzz.py を作って 1〜30 を出力して実行して" | cline --cwd /content/workspace --auto-approve true
```

同じ文字列でも標準入力経由なら問題なく処理される。`scripts/50_run.sh` は
この方式に修正済み（最後の引数をプロンプトとして取り出し、`echo | cline` で渡す）。
ターミナルで `cline` を対話起動して日本語で入力する場合はこのバグの影響を受けない
（引数パーサーではなく対話 REPL の入力経路を通るため）。

# 作業の区切りごとに

## 10. 実機で潰すべき検証項目

**V-1 と V-2 が最優先。この 2 つでこの構成が使い物になるかが決まります。**

| ID | 検証内容 | 判定基準 | 変わりうる設計 | 手段 |

## 12. colab CLI による手元からのリモート制御

ノートブック UI を開かず、**手元のシェルから VM を立てて操作する**経路。
§4 の T1〜T3（ターミナルボタン / セル / VS Code 拡張）を置き換えるものではなく、
**モデルを差し替えて何度も評価を回す**ための自動化層として足した。

### 12.1 前提: colab CLI は git から入れる

`colab ssh` は **v0.7.0（2026-09-03）で追加された**が、
**PyPI には 0.6.0 までしか出ていない**（2026-09-17 時点）。git tag は v0.7.1 まである。

```bash
uv tool install --force "git+https://github.com/googlecolab/google-colab-cli@v0.7.1"
colab version   # -> 0.7.1
```

0.6.x のままだと `colab ssh` が無く、`colab exec`（Python 実行・既定 timeout 30 秒）
を迂回路として使うことになる。`remote/common.sh` は版を検査して 0.7.0 未満なら止まる。

`colab ssh` でできること:

- SSH over WebSocket。`root@colab-runtime` にログインし `/content` に着地する
- **`--proxy-mode` が OpenSSH の `ProxyCommand` 互換** → `ssh` / `scp` / `rsync` /
  VS Code Remote-SSH がそのまま通る
- 鍵は `id_ed25519` → `id_ecdsa` の順。**RSA はサーバ側で拒否される**
- `--rm` で切断時に VM を停止できる

### 12.2 使い方

> **実際に手を動かす手順は [リモート運用ガイド.md](リモート運用ガイド.md) にある。**
> ここは全体像だけ。準備・期待される出力・トラブルシュートはガイド側。

```bash
bash remote/00_all.sh --help # ★一括実行（下を順番に呼ぶだけ）
bash remote/00_doctor.sh     # 手元側の前提確認（VM は作らない＝課金しない）
bash remote/01_new.sh        # VM 確保 + ssh 経路の検証
bash remote/02_deploy.sh     # 作業ツリーを VM へ同期
bash remote/03_setup.sh      # Ollama + Cline + Codex（10〜20 分）
bash remote/04_attach.sh     # VM のシェルに入る
bash remote/04_attach.sh codex   # そのまま codex TUI
bash remote/09_stop.sh       # ★成果物を回収して停止
```

モデルを変えるときは `MODEL_PROFILE` を渡すだけでよい（§12.3）:

```bash
MODEL_PROFILE=gpt-oss-20b bash remote/03_setup.sh
```

**認証**は `COLAB_AUTH`（既定 `oauth2`）で選ぶ。`adc` を使う場合は
**スコープ 4 つを明示**して取り直すこと。1 つでも欠けるとセッション確保か
キープアライブが 401/403 で落ちる:

```bash
gcloud auth application-default login \
  --scopes=openid,\
https://www.googleapis.com/auth/cloud-platform,\
https://www.googleapis.com/auth/userinfo.email,\
https://www.googleapis.com/auth/colaboratory
```

`colab auth` は **VM 側**に GCP 認証情報を入れる別コマンド。
CLI 側の 401/403 の対処には使えない。

### 12.3 モデルプロファイル

モデルを差し替えるたびに `BASE_MODEL` / `NUM_CTX` / `CODEX_TOOL_REPAIR` /
`AGENTS.md` の内容を個別に合わせるのは間違えやすいので、組み合わせに名前を
付けた（`scripts/common.sh`）。優先順位は
**明示した環境変数 > プロファイル > 従来の既定値**で、
`MODEL_PROFILE` を指定しなければ従来とまったく同じ挙動になる。

| プロファイル | BASE_MODEL | NUM_CTX | KV MiB/tok | 修復プロキシ | AGENTS ルール |
|---|---|---:|---:|:--:|---|
| `qwen3-8b` | `qwen3:8b` | 32768 | 0.07 | 0 | minimal |
| `qwen3-14b` | `qwen3:14b` | 16384 | 0.08 | 0 | minimal |
| `gpt-oss-20b` | `gpt-oss:20b` | 16384 | 0.024 | 0 | minimal |
| `qwen25-coder-14b` | `qwen2.5-coder:14b-instruct-q4_K_M` | 16384 | 0.094 | **1** | apply-patch-workaround |

**`AGENTS.md` の中身をモデルによって変えるのが要点。** §5.8.1 の回避策
（「apply_patch を使うな、heredoc で全体を書け」）は qwen2.5-coder 専用で、
apply_patch 形式の編集で訓練されたモデルに同じことを言うと、得意な経路を
わざわざ塞ぐことになる。テンプレートは `scripts/agents/` に置き、
`AGENTS_RULESET` で選ぶ。

**修復プロキシ（§5.8）も既定をプロファイル依存にした。** 壊れていないモデルに
噛ませても益は無く、ストリーミング表示を 1 チャンクに潰す副作用だけが残る。

### 12.4 pull する前に VRAM に載るか判定する

`20_ollama.sh` の VRAM 確認は、もともと**モデルをロードした後**にしか無かった。
これだと 13〜15GB のモデルを落としきってから「載りません」と分かる。

`scripts/vram_precheck.py` は **Ollama のレジストリからマニフェスト（数 KB）だけを
引いて**重みのサイズを求め、`nvidia-smi` の空き VRAM と `NUM_CTX` から必要量を
見積もって、足りなければ pull の前に止める。

```
      モデル       : devstral-small-2:24b-instruct-2512-q4_K_M
      重み         :    14474 MiB (14.14 GiB)
      KV (ctx=16,384) :     1278 MiB  @ 0.078 MiB/token
      計算バッファ :      640 MiB
      ---------------------------------------------
      必要量       :    16392 MiB (16.01 GiB)
      空き VRAM    :    14913 MiB (14.56 GiB)
      余裕         :    -1479 MiB

      判定: NG — 1479 MiB 足りません。
```

どうしても試すなら `FORCE_VRAM=1`（層が CPU にあふれ、極端に遅くなる）。

**測る前にロード済みモデルを降ろすこと**が実装上の要点。`OLLAMA_KEEP_ALIVE=-1`
にしているため前のモデルは VRAM に居座り続け、その状態で「空き」を測ると
載るはずのモデルまで NG になる（実機で踏んだ: qwen3:8b が 7.7GB 占有していて
空きが 7412 MiB しかなく、gpt-oss:20b が -6776 MiB と誤判定された）。

### 12.5 実機で踏んだ罠

**(1) SSH セッションでは `LD_LIBRARY_PATH` が空 —— Ollama が黙って CPU に落ちる**

Colab のノートブックカーネルは `LD_LIBRARY_PATH=/usr/lib64-nvidia` を設定するが、
**素の SSH ログインには引き継がれない**。GPU デバイス（`/dev/nvidia0`）は
見えているのに:

```
NVIDIA-SMI couldn't find libnvidia-ml.so library in your system
```

怖いのは `nvidia-smi` が落ちることではなく、**Ollama が CUDA を検出できずに
エラーも出さずに CPU へフォールバックする**こと。推論が一桁遅くなり、
ベンチの数字が丸ごと無意味になる。

環境変数ではなく **ldconfig で直す**。そうすれば Ollama をどう起動しても効く:

```bash
echo /usr/lib64-nvidia > /etc/ld.so.conf.d/colab-nvidia.conf
ldconfig
```

`remote/common.sh` の `vm_bootstrap_env()` が `01_new.sh` から自動で実行し、
直ったことを `nvidia-smi -L` で確認するところまでやる。効いていれば
`ollama.log` に次が出る:

```
msg="inference compute" library=CUDA compute=7.5 name=CUDA0 description="Tesla T4"
```

**(2) `A && B && C & echo $!` は `&` がチェーン全体にかかる**

```bash
# 誤り: mkdir が終わる前に echo が走る
mkdir -p /content/logs && cd /x && setsid nohup ... & echo $! > /content/logs/setup.pid
#   -> /content/logs/setup.pid: No such file or directory
```

バックグラウンドにしたいのは最後のコマンドだけなので、区切りは `;` にする。

**(3) `pgrep -f` は ssh 越しだと自分自身を拾う**

`ssh host -- "pgrep -f '00_setup_all.sh'"` は、リモートシェルのコマンドラインにも
その文字列が載るため**常にヒットする**。パターンの一部を文字クラスにして避ける:

```bash
pgrep -f '[0]0_setup_all\.sh'
```

**(4) `tail -f | sed /q` はログが静かになると永久に止まる**

セットアップの完了を「センチネル行が出たら抜ける」で待っていた:

```bash
rsh "tail -n +1 -f '$SETUP_LOG'" | sed "/$SENTINEL/q"   # ← 30 分ハングした
```

`sed` は**正しく動いている**。センチネル行を出力して終了する。問題は左側で、
**SIGPIPE は「次に書き込んだとき」にしか配送されない**。セットアップが終われば
ログは静かになるので、`ssh`/`tail -f` は二度と書き込まず、シグナルを受け取る
機会がないまま待ち続ける。**ログが流れ続ける前提でしか成立しない書き方だった。**

`tail -f | head -1` や `tail -f | grep -m1` もまったく同じ理由で止まる。

対処は「パイプの右側で抜ける」のをやめ、**リモート側でポーリングして
リモート側から抜ける**こと。ssh の終了はリモートコマンドの終了で決まるので、
SIGPIPE に依存しなくなる（`remote/03_setup.sh` 手順 3）。
無限待ちを避けるため `SETUP_WAIT_MAX`（既定 5400s）で上限も設けた。

**(5) ヘッダ無しの CSV は読み違える**

`scripts/10_preflight.sh` は `memory.used` を、`remote/01_new.sh` は
`memory.free` を、どちらも `--format=csv,noheader` で出していた。並びが同じなので
`0 MiB` を見て「空き容量ゼロ」と誤診した（実際には「使用中ゼロ」＝正常）。
項目名を併記して区別できるようにした。

### 12.6 停止忘れが最大のリスク

`colab stop` しない限り、キープアライブが 24 時間回り続けてコンピューティング
ユニットを消費する。`remote/*.sh` はどれも失敗時に停止手順を表示する。

`09_stop.sh` は停止前に `logs/` `.cline-env/` `workspace/` を
`artifacts/<セッション名>-<日時>/` へ回収する。**VM はステートレスなので、
止めた瞬間に全部消える。**

### 12.7 gpt-oss:20b の 2 つのツール呼び出し不具合と対策

`MODEL_PROFILE=gpt-oss-20b` が修復プロキシを有効（`CODEX_TOOL_REPAIR=1`）に
しているのは、§5.8 の「タグ無し JSON の修復」が目的ではなく、以下 2 つのため。
どちらも 2026-09-17 に実機（T4 / Ollama 0.34.1 / codex-cli 0.154.0）で観測した。

#### (1) Ollama が自分の出力をパースできず 500 を返す（ollama/ollama#17638）

```
stream disconnected before completion: error parsing tool call:
  raw='{"cmd":"apply_patch <<'PATCH' ... PATCH"]}',
  err=invalid character ']' after object key:value pair
```

`"cmd":` の値が**文字列として開かれているのに配列として閉じられている**
（開き括弧が無く末尾に `]` だけ残る）。エラーを出しているのは Codex ではなく
**Ollama サーバ自身**で、HTTP 500 を返す。

[ollama/ollama#17638](https://github.com/ollama/ollama/issues/17638)（2026-08-09
報告・未修正）。発生条件は「単一のフリーフォーム文字列引数を取る patch 系
ツール」「長いツール説明文」「複数ターン」で、**非決定的**（報告ではおおむね
5 回中 2 回）。

原因は上流にあり、プロキシからは生のテキストが見えない（Ollama の内部で落ちる）
ため修復はできない。だが非決定的なので、**この 500 に限って投げ直す**。

実測: 5 回の試行で再送が 16 回発火し、**15 回が救済成功**（諦めたのは 1 回）。
`stream disconnected` は 1 度も再現しなくなった。

`CODEX_PROXY_TOOLCALL_RETRIES`（既定 3）で回数を変えられる。0 で無効。
検証は `scripts/test_tool_proxy_retry.py`。

#### (2) harmony のチャネル構文を本文に書き出してツール呼び出しを発行しない

(1) を再送で潰しても、5 回中 2 回は**別の理由**で失敗した。本文にこう出る:

```
Given ambiguity, perhaps we should use `commentary to=functions.exec_command` to ...
Use:
commentary to=functions.apply_patch <|constrain|>json<|message|>{"patch":"..."}

tokens used 9,196
```

gpt-oss は本来 harmony のチャネル構文で構造化出力を出すが、**その構文を
そのままプレーンテキストとして本文に書き**、ツール呼び出しを発行しないまま
「どう呼ぼうか」と延々と悩んで出力トークンを使い切る
（`model_max_output_tokens = 8192` に対し 9,196 / 12,936 トークン使って打ち切り）。
結果、ファイルが 1 つも作られないか、途中まで書かれた空に近いファイルが残る。

**これは §5.6 / §5.8 とまったく同じ系統の症状**（構造化出力にせずテキストで
返す）だが、harmony では**ツール名が JSON の外側**（`to=functions.NAME`）に
あるため、既存の `{"name":..., "arguments":...}` を探す修復では拾えなかった。

対策として `_find_harmony_tool_calls()` を追加し、次の形を拾って正しい
`tool_calls` に組み替える:

```
to=functions.<NAME> [<|constrain|>json] [<|message|>] {引数の JSON}
```

誤爆を避けるため、**ツール名が実際に渡されたツール一覧にあり、かつ直後に
パース可能な JSON が続く場合だけ**拾う。単に
「`to=functions.exec_command` を使えばよい」と言及しただけの文（JSON が
続かない）は拾わない。検証は `scripts/test_tool_proxy_harmony.py`。

#### 実測サマリ（プロンプト: `pythonでfizzbuzzを書いてテストして。` × 5）

再送のみ（harmony 対応前）:

| 試行 | fizzbuzz.py | test_fizzbuzz.py | 原因 |
|---|---:|---:|---|
| 1 | なし | なし | (2) トークン切れ |
| 2 | 1394 B | 333 B | ✓ |
| 3 | 7 B | なし | (2) トークン切れ |
| 4 | 1146 B | 504 B | ✓ |
| 5 | 962 B | 475 B | ✓ |

#### harmony 修復の実機検証（モデル不要・2026-09-17）

T4 が `Service Unavailable` で取れず、CPU ランタイム（RAM 約 12.7GB）では
13GB の gpt-oss:20b が載らない。そこで**モデルを使わずに**、プロキシの上流を
スタブに差し替えて検証した（`scripts/test_harmony_e2e_stub.py`）:

```
Codex CLI  ->  32_codex_tool_proxy.py  ->  スタブ（実機で観測した本文を返す）
```

ユニットテストでは「テキストから tool_calls を組み立てられるか」までしか
確かめられない。本当に知りたいのは **Codex が修復後の tool_calls を受け取って
実際にツールを実行するか**で、この構成ならモデル無しでそこまで見られる。

条件を 1 つだけ変えた A/B（経路も SSE 包装も同一）:

| ツール名 | プロキシの判定 | codex exit | ファイル作成 |
|---|---|---:|:--:|
| `exec_command`（実在する） | **repaired** | 0 | **された** |
| `this_tool_does_not_exist` | passthrough | 0 | されない |

修復が発火した側でのみ Codex が実際にコマンドを走らせた:

```
/bin/bash -lc 'echo HARMONY_REPAIR_WORKS > /content/workspace/harmony_proof.txt'
```

**この検証で分かった副次的な事実:**

- Codex 0.154.0 が渡すツールは `exec_command` / `write_stdin` /
  `request_user_input` / `view_image` / `multi_agent_v1` / `get_goal` /
  `create_goal` / `update_goal` と、`type: web_search`（name 無し）
- **`apply_patch` はツールとして提供されていない。** §12.7 (1) で観測した
  `{"cmd":"apply_patch <<'PATCH' ..."}` は、モデルが `exec_command` の `cmd`
  （**string 型**）からシェル経由で apply_patch を呼ぼうとしたもの。
  `cmd` が string である以上、末尾の `]` は完全にモデルの誤りであり、
  #17638 の「array-wrap してしまう」という説明と一致する

**注意**: これは修復ロジックと Codex の受け取りを検証したものであり、
「gpt-oss の成功率が 3/5 からどれだけ上がるか」は測っていない。
それには T4 と実モデルが要る。

#### 実機検証を再現する手順

```bash
COLAB_GPU=cpu bash remote/01_new.sh      # GPU 不要
bash remote/02_deploy.sh
# VM 上で Node 22 + codex を入れ、スタブとプロキシを起動して codex exec
# 詳細は scripts/test_harmony_e2e_stub.py の docstring
```

## 13. GPU が取れないときに先へ進む — 3 層の検証レーン

### 問題

無料枠の T4 は取り合いで、確保できないことのほうが多い。にもかかわらず、
このリポジトリは長らく **GPU が無いと 1 行も進めない**作りだった:

- `scripts/10_preflight.sh` は `nvidia-smi` が無ければ即 `die`
- `scripts/20_ollama.sh` は無条件に `nvidia-smi` を叩く

しかし、この構成で確かめたいことの **半分は GPU を必要としない**。

### 分類

| レーン | 場所 | 確定できること | GPU |
|---|---|---|:--:|
| **L1** モデル不要 | どこでも | 修復プロキシの修復ロジック、エージェントが何秒で切るか、配線（`config.toml` / `providers.json`） | 不要 |
| **L2** CPU 実モデル | CPU 環境 | モデルが**本当に** `tool_calls` を返すか。漏れるならその生の形 | 不要 |
| **L3** T4 実機 | Colab T4 | 実用速度、安全プロンプト長、実タスクの完走率 | 必要 |

**L3 だけが T4 を要する。** L1/L2 を CPU に寄せておけば、確保できた T4 の
時間を L3 に使い切れる。

L1 と L2 の成果は循環する: L2 で採った**生の応答**が L1 のテストデータになり、
L1 で直した修復ロジックを L2 で再確認する。

### 使い方

```bash
# L1 + L2 を一括
MODEL_PROFILE=gemma4-12b-qat bash scripts/60_cpu_verify.sh

# 重みが要らない範囲だけ（L1）
SKIP_MODEL=1 bash scripts/60_cpu_verify.sh
```

レポートは `$STATEDIR/cpu-verify-report.md` に出る。

### ACCEL — GPU/CPU の判定を 1 か所に閉じ込める

`scripts/common.sh` が `ACCEL`（`gpu` / `cpu`）を決め、各スクリプトはこれを見る。
未指定なら `nvidia-smi` の有無で自動判定する。

CPU では `OLLAMA_FLASH_ATTENTION` と `OLLAMA_KV_CACHE_TYPE` の既定も変わる。
Ollama の KV キャッシュ量子化（`q8_0`）は FlashAttention が有効なときにしか
効かず、CPU バックエンドでは FlashAttention が使えないため、GPU 用の値を
そのまま渡しても得が無い。

メモリの問い合わせは `accel_free_mib` / `accel_mem_label` / `accel_mem_report`
に集約してある。`scripts/vram_precheck.py` は判定ロジックを 1 本のまま、
第 7 引数で表示ラベル（`VRAM` / `RAM`）だけを切り替える。

> **出力 JSON のパスとキーは変えていない。** `20_ollama.sh` の pull 前の警告が
> `$STATEDIR/vram-precheck.json` の `weights_mib` を読んでいるため（§12.5 も参照）。

### ★ レジストリが塞がれている環境では pull を試みない

`ollama.com`（インストーラの配布元）と `registry.ollama.ai`（重みの配布元）は
**別のホスト**で、後者だけが egress ポリシーで塞がれている環境が実在する。
その場合、ollama のインストールまでは通ってから `pull` だけが失敗する。

`10_preflight.sh` は両方を独立にチェックし、結果を
`$STATEDIR/net-registry-ok` に残す。`60_cpu_verify.sh` はそれを読んで、
届かないときは **pull を試みずに、許可すべきホストを名指しして** L2 を飛ばす。

```
registry.ollama.ai に到達できないため、モデルを要する段 (L2) を飛ばします。
ollama pull は必ず失敗するので、待つ意味がありません。
```

### CPU での数字の扱い

`20_ollama.sh` のベンチは CPU でも動くが、**判定は参考値**である。
CPU で 12B 級を回せば生成は数 tok/s になり、判定はまず NG になる。
モデル選定の根拠にしてはいけない。進捗の把握（生きているか、あとどれくらいか）
に使う。速度の評価は L3 の仕事。

### CPU では Cline のタイムアウトが効いてくる

§7 の訂正のとおり Cline CLI 3.0.62 の既定は 300 秒で、T4 ならまず当たらない。
だが **CPU で 12B 級を回すと prefill だけで数分かかる**ため、300 秒に当たりうる。

```bash
bash scripts/33_patch_cline_timeout.sh              # 600 秒に引き上げ
CLINE_TIMEOUT_MS=1800000 bash scripts/33_patch_cline_timeout.sh
bash scripts/33_patch_cline_timeout.sh --show       # 現在値
bash scripts/33_patch_cline_timeout.sh --restore    # 戻す
```

定数は minify されて版ごとに違う記号名になっているため、
エクスポート名 `OLLAMA_DEFAULT_TIMEOUT_MS` から記号を引いて書き換える。
**候補が 1 個に定まらなければ `die` する**（「パッチしたつもりで効いていない」が
いちばん困る失敗なので、黙って進めない）。

> **`npm install -g cline` をやり直すとパッチは消える。** 版を上げたら再適用すること。

### Colab の CPU ランタイムを使う手もある

手元のマシンや Claude on the web ではなく、Colab の CPU ランタイムでも L2 は回る
（GPU 枠を消費しない）。

```bash
bash remote/00_all.sh --gpu cpu --profile gemma4-12b-qat
```

ただし無料の CPU ランタイムは RAM 約 12.7GB なので、重み 7.2GB のモデルでは
`num_ctx` を絞る必要がある。事前チェックが RAM に対して判定する。
