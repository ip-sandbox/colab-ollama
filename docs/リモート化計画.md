# 計画: colab CLI による Colab VM のリモート制御 + モデル差し替え評価

対象: `ip-sandbox/colab-ollama` / 2026-09-17

---

## Context — なぜこれをやるか

この構成は今、**Colab のノートブック UI / ターミナルボタンの中から手で叩く**前提
（手順書 §4 の T1〜T3）になっている。そのため手元のエディタから一気通貫で回せず、
**モデルを差し替えて比較評価する**たびに同じ手作業を繰り返すことになる。

本来の目的は後者 —— Qwen-Coder 系から別モデルに差し替えて、Codex CLI の
エージェントとしてどこまで使えるかを比較評価すること。そのために
「手元のシェルから VM を立て、環境を作り、エージェントに入り、評価を回して落とす」
足場を [`google-colab-cli`](https://github.com/googlecolab/google-colab-cli) で作る。

## 0. 調査で確定した事実（計画の前提を変えるもの）

### 0.1 `colab ssh` は使える — ただし PyPI 版には入っていない

| | |
|---|---|
| 追加バージョン | **v0.7.0（2026-09-03）** `#88` |
| PyPI の最新 | **0.6.0 のみ**（= 手元に入っている版。`ssh.py` が無い） |
| git tag | **v0.7.1 まで存在** |

→ **git から入れ直せば使える。**

```bash
uv tool install --force "git+https://github.com/googlecolab/google-colab-cli@v0.7.1"
```

`colab ssh` の仕様（`src/colab_cli/commands/ssh.py` を実読して確認）:

- SSH over WebSocket。ログイン先は `root@colab-runtime`、着地は `/content`
- フラグ: `-s/--session`, `--gpu`, `--tpu`, `--high-mem`, `-i/--identity`, `--rm`, `--proxy-mode`
- `-s NAME` のセッションが無ければ**自動で作る**（`--gpu/--tpu` はその際の指定）
- `--rm` で切断時に VM を停止
- **`--proxy-mode` は OpenSSH の `ProxyCommand` 互換**。`~/.ssh/config` に書けば
  **`ssh`/`scp`/`rsync`/VS Code Remote-SSH がそのまま使える**
- 鍵は `id_ed25519` → `id_ecdsa` の順。**RSA はサーバ側で拒否される**

v0.7.0 では他に `colab exec/run` の `--env KEY=VALUE` と `--high-mem` も入っている。

**これは設計を大きく単純化する。** 0.6.0 前提で必要だった「`colab exec` に Python
ワンライナーを渡して `subprocess` でシェルを回す」「30 秒 timeout を避けるため
デタッチ起動してログをポーリングする」という迂回が**全部不要**になり、
普通の `ssh`/`rsync` になる。

### 0.2 TPU v5e-1 では Ollama が動かない

無料枠は T4 と TPU v5e-1 のみ（ユーザー確認済み）。だが:

- **Ollama / llama.cpp に TPU バックエンドは存在しない。** GGUF の実行先は
  CUDA / Metal / Vulkan / ROCm / SYCL のみ。llama.cpp の TPU 対応は
  [issue #11603](https://github.com/ggml-org/llama.cpp/issues/11603) が
  **未実装の feature request** のまま
- TPU 推論の正道は vLLM + `tpu-inference` プラグイン、または Optimum-TPU（JAX）。
  つまり**このリポジトリの Ollama 前提のスタック（Modelfile / num_ctx /
  keep_alive / 修復プロキシ / ベンチ）を全部作り直す**ことになる
- しかも **v5e-1 の HBM は 16GB/チップ**。TPU 側は GGUF 4bit が使えないので
  bf16 か int8 になり、24B は bf16 で 48GB / int8 で 24GB → **どちらも載らない**

→ **TPU は今回採らない。** 採るなら「Ollama をやめて vLLM/JAX に移る」という
別プロジェクトとして切る。

### 0.3 Gemma + Antigravity は「ローカルモデル」としては成立しない

2 段で駄目になる。

**(a) Antigravity 側** — IDE も CLI (`agy`) も **BYOK / ローカルエンドポイント非対応**。
モデルは Vertex Model Garden の固定リストで、`localhost:11434` を向ける手段が無い。
非公式ラッパー（`vahapogut/free-antigravity-cli` 等）は内部バンドルにパッチを当てる
方式で、更新のたびに壊れ ToS にも触れる。→ **採らない。**

**(b) Gemma 側** — **Gemma 3 は Ollama のテンプレートに tool calling が入っていない**
（ollama ライブラリの capabilities に `tools` が無い）。これは手順書 §5.6 で
qwen2.5-coder:7b が落ちたのと**まったく同じ罠**で、エージェントの土台にはできない。
コミュニティの `*/gemma3-tools` 系ファインチューンはあるが、検証コストが見合わない。

**ただし Antigravity CLI (`agy`) 自体は使い道がある。** Go 単一バイナリ、
headless の `-p`（print mode）、**リモート SSH セッション向けに最適化**と明記されており、
`colab ssh` と相性が良い。ただし動かすモデルは **Gemini（クラウド）** になるため
「ローカル LLM」という本構成の前提からは外れる。
→ **比較の「上限の基準線」としてなら価値がある**（§3 の未決事項）。

### 0.4 Devstral Small 2 24B Q4 は T4 に載らない（実機で確認済み）

> 当初この節の VRAM は「T4 は 16GB のカード」からの**推定値（約 15.0 GiB）**で書いていた。
> 2026-09-17 に実測したところ実際の空きは **14913 MiB = 14.56 GiB** で、推定は
> 約 450 MiB 楽観的だった。以下は実測値に置き換えてある。

`devstral-small-2:24b-instruct-2512-q4_K_M` = 15GB ≈ **14.0 GiB**。
T4 の使用可能 VRAM は **14913 MiB = 14.56 GiB**（実測。総容量 15360 MiB のうち
447 MiB はドライバ予約で使えない）。KV(q8_0) は約 0.078 MiB/token なので
**num_ctx を 8192 まで削っても枠を超える**。
実際に事前チェックにかけたところ **必要 16392 MiB / 余裕 -1479 MiB** で NG だった。
Ollama 公式タグに q4_K_M より小さい量子化は無い（q4_K_M / q8_0 / fp16 のみ）。
L4 なら余裕だが**無料枠では L4 を引けない**（ユーザー確認済み）。→ **✕。**

## 2. フェーズ 1 — 足場（`colab ssh` 前提）

VM 側のスクリプト（`scripts/NN_*.sh`）は**作り直さない**。
`00_setup_all.sh --with-codex` はそのまま再利用し、手元から呼ぶ層だけ足す。

### 2.1 新規: `remote/`

| ファイル | 役割 |
|---|---|
| `remote/common.sh` | セッション名 / `--gpu` / `--auth=adc` / `--config` を一元管理。`colab` の版を検査し、**0.7.0 未満なら git から入れ直す手順を表示して止める** |
| `remote/00_doctor.sh` | 前提確認: `colab` の版、ADC のスコープ、`~/.ssh/id_ed25519` の有無（無ければ ed25519 鍵の作り方を表示）、`~/.ssh/config` のホスト定義 |
| `remote/01_new.sh` | `colab new -s $SESSION --gpu $COLAB_GPU` + `nvidia-smi` で実機確認 |
| `remote/02_deploy.sh` | `rsync -e 'ssh -F remote/ssh_config'` で作業ツリーを VM へ同期（git clone より速く、未コミットの変更も乗る） |
| `remote/03_setup.sh` | ssh 越しに `00_setup_all.sh --with-codex` を実行（`tmux`/`nohup` で切断耐性を持たせる） |
| `remote/04_attach.sh` | `colab ssh -s $SESSION` でシェルに入る（ここで `codex` TUI） |
| `remote/05_eval.sh` | 評価タスクを非対話実行し、結果を `rsync` で回収 |
| `remote/09_stop.sh` | `colab stop`。ログを先に回収 |
| `remote/ssh_config.tmpl` | `ProxyCommand colab ssh --proxy-mode -s %n` を含む雛形。**VS Code Remote-SSH もこれで繋がる** |

### 2.2 認証（ここを外すと全部 401/403 で止まる）

- `--auth` は **`adc` を常時明示**。手元 0.6.0 の `--help` は既定 `oauth2`、
  付属スキルドキュメントは `adc` と**食い違っている**ため、暗黙値に頼らない
- ADC は**スコープ 4 つ**を明示して取り直す（1 つ欠けるとセッション確保か
  キープアライブが落ちる）。ブラウザが開くので**人が 1 回だけ手で実行**する:

  ```bash
  gcloud auth application-default login \
    --scopes=openid,\
  https://www.googleapis.com/auth/cloud-platform,\
  https://www.googleapis.com/auth/userinfo.email,\
  https://www.googleapis.com/auth/colaboratory
  ```

- `colab auth` は **VM 側**に GCP 認証情報を入れる別物。CLI の 401/403 対処に使わない

### 2.3 安全弁

- **停止忘れが最大のリスク。** `colab stop` しない限り 24 時間キープアライブが
  回り続ける。`remote/*.sh` は失敗時に必ず停止コマンドを表示する
- 使い捨て用途では `colab ssh --rm` を使うと切断時に自動停止する
- `--gpu` に未知の値を渡すと**黙って A100 にフォールバックする**（付属スキル
  ドキュメントに明記）。`remote/common.sh` で `T4|L4|G4|H100|A100` に限定して弾く

## 3. フェーズ 2 — VM 側の改修（モデル切り替えの一変数化）

### 3.1 `scripts/common.sh` — `MODEL_PROFILE`

いま `BASE_MODEL` / `NUM_CTX` / `CODEX_TOOL_REPAIR` を個別に指定する必要がある。
モデルごとに適切な組み合わせが違うので **1 変数で切り替わる**ようにする。
未指定なら現在の挙動を保つ（後方互換）。個別の環境変数上書きは従来どおり効かせる。

| プロファイル | BASE_MODEL | NUM_CTX | TOOL_REPAIR | 位置づけ |
|---|---|---:|:--:|---|
| `qwen3-8b` | `qwen3:8b` | 32768 | 0 | 現行既定。**据え置き**（後方互換のため残す） |
| `gpt-oss-20b` | `gpt-oss:20b` | 16384 | 0 | **評価対象①** |
| `qwen3-14b` | `qwen3:14b` | 16384 | 0 | **評価対象②** |

`qwen2.5-coder-14b` プロファイルは作らない（候補外の指示）。
ただし `BASE_MODEL` の直接指定は従来どおり効くので、必要になれば手で指定できる。

### 3.2 `scripts/20_ollama.sh` — pull 前の VRAM 事前チェック

現状、VRAM 確認は**モデルをロードした後（手順 7）**にしか無い。
これだと 15GB 落としきってから「載りません」と分かる。
**`ollama pull` の前**にレジストリのマニフェストから重みサイズを取り、
`nvidia-smi` の空き VRAM と `NUM_CTX` から必要量を見積もって、
足りなければ **pull する前に止める**（`--force` で続行可）。

**これにより「載るか」を表で当てずに機械的に判定できる。** §0.4 のような
判断を毎回手でやらずに済む。

### 3.3 `scripts/31_alt_agents.sh` — AGENTS.md と修復プロキシをプロファイル依存に

現在配置している `AGENTS.md` は **qwen2.5-coder 専用の回避策**
（「apply_patch を使うな、heredoc で全体を書け」）。他モデルには逆効果になりうる。
修復プロキシ（`32_codex_tool_proxy.py`）も、壊れていないモデルに噛ませると
ストリーミング表示を 1 チャンクに潰すだけで益が無い。両方プロファイル依存にする。

### 3.4 `scripts/10_preflight.sh`

VRAM しきい値（7000 / 13000 MiB）が 7B・14B 前提。判定を見直す。

## 4. フェーズ 3 — 評価ハーネス（`scripts/60_eval.sh` + `remote/05_eval.sh`）

**同一タスクを複数モデルに投げ、同じ指標で比べる。** 非対話実行（`codex exec`）。

| # | タスク | 何を見るか |
|---|---|---|
| E-1 | `fizzbuzz.py` を作って実行 | 1 ファイル作成 + シェル実行 |
| E-2 | `test_fizzbuzz.py` を足して `pytest` を通す | 複数ファイル + 自己検証ループ |
| E-3 | 既存ファイルの一部を書き換える | 部分編集（apply_patch / heredoc） |
| E-4 | 存在しない関数を呼ぶバグを直す | 読む→直す→再実行の往復 |

`$STATEDIR/eval-<プロファイル>.json` に記録する指標:

- 完走したか / 何ターンで終わったか / 経過秒数
- **生成されたファイルが空でないか**（手順書 §5.8.1 の不具合検出）
- `pytest` が通ったか
- prefill tok/s, generation tok/s（`20_ollama.sh` のベンチ値を併記）
- ツール呼び出し回数 と **テキストだけで終わりツールを呼ばなかったターン数**

最後の指標が要。いま 14B で起きている「コマンドを提示するだけで実行しない」を
数値で捕まえるため。

## 5. 評価対象（確定）

**`gpt-oss:20b` と `qwen3:14b` の 2 つ。** Antigravity CLI (`agy`) は今回含めない
（理由は手順書 §5.11 に残す）。

### 5.1 `gpt-oss:20b` — 本命だが T4 ではぎりぎり

- Ollama 公称 **14GB ≈ 13.0 GiB**。capabilities に `tools` と `thinking` の両方
- MoE。MXFP4（4.25 bit/param）で量子化済み。公称「16GB メモリで動く」
- KV は 24 層 / KV ヘッド 8 / head_dim 64 と小さく、q8_0 で約 0.023 MiB/token。
  **num_ctx=16384 で約 0.4 GiB** → 合計 13.0 + 0.4 + バッファ ≈ **約 14 GiB**。
  T4 の実測空き 14913 MiB (14.56 GiB) には**収まる計算**だが余裕は 1 GiB 程度
  （→ 実機では 12499 MiB 使用 / 2414 MiB 空きで、予測より余裕があった）

**未検証のリスクが 2 つある。どちらも §3.2 の事前チェックと §4 のベンチで実測する:**

1. **MXFP4 が T4（sm_75 / Turing）で動くか。** Ollama は新エンジンで MXFP4 カーネルを
   独自に持つが、公式に最低 compute capability の記載が無い。Blackwell 系のような
   ネイティブ FP4 テンソルコア加速は当然効かないので、**動いても遅い可能性**がある
2. **`thinking` が 30 秒予算を食う。** 手順書 §5.4 の警告がそのまま当たる。
   ただし gpt-oss は reasoning effort を指定できるので、プロファイルで
   **低めに固定する**ことを試す（`20_ollama.sh` のベンチが `<think>` を検出する
   既存ロジックをそのまま流用できる）

**先に `gpt-oss:20b` から測る。** ここで MXFP4 が T4 で成立しないと分かれば、
`qwen3:14b` に労力を寄せられる。

### 5.2 `qwen3:14b` — 手堅い方

- 約 9GB。`tools` + `thinking`。T4 に余裕を持って載る
- `qwen3:8b`（現行既定）と同系列なので、**8b → 14b でエージェント能力が
  どれだけ伸びるか**という素直な比較になる
- 思考トークンの予算食いは §5.4 の警告どおり注意が必要

### 5.3 `qwen3:8b` の扱い

プロファイルとしては**据え置きで残す**（現行既定・後方互換）。
`20_ollama.sh` のベンチは毎回走るので、**比較用の数字は追加コストゼロで取れる**。
評価タスク（E-1〜E-4）まで回すかは、上記 2 つを測ってから判断すればよい。

## 6. 検証方法

```bash
# フェーズ 1
bash remote/00_doctor.sh              # -> colab >= 0.7.0 / ADC 4 スコープ / ed25519 鍵 が揃う
bash remote/01_new.sh                 # -> colab sessions に出る
colab ssh -s $SESSION -- nvidia-smi   # -> T4 が返る（ssh 経路が通っていることの証明）
bash remote/02_deploy.sh              # -> VM 上に作業ツリーが同期される
bash remote/03_setup.sh               # -> 完走。ollama list に cline-coder がある
ssh -F remote/ssh_config colab-t4 -- 'nvidia-smi'   # -> ProxyCommand 経由でも通る
bash remote/04_attach.sh              # -> codex TUI が出る（目視）
bash remote/09_stop.sh                # -> colab sessions が空

# フェーズ 2
MODEL_PROFILE=gpt-oss-20b bash remote/03_setup.sh
#   -> pull 前チェックを通過し、ollama list に載る
#   -> nvidia-smi で VRAM 使用量が約 14GiB / 空きが 1GiB 前後であること
#   -> ベンチが prefill/generation tok/s を出す（MXFP4 が T4 で成立するかの判定）
BASE_MODEL=devstral-small-2:24b-instruct-2512-q4_K_M bash remote/03_setup.sh
#   -> 15GB を pull する前に止まること（事前チェックの回帰確認）

# フェーズ 3
MODEL_PROFILE=gpt-oss-20b bash remote/05_eval.sh
MODEL_PROFILE=qwen3-14b   bash remote/05_eval.sh
# -> eval-*.json が揃い、RESULT.md の比較表が埋まる
```

各フェーズは**必ず `remote/09_stop.sh` で締める**。停止したことを
`colab sessions` が空になることで確認する。
